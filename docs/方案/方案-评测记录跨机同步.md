# 方案：评测记录跨机同步（git 文本导出 + 本地库收敛）

日期：2026-09-07 · 状态：**设计定稿，待实现** · 关联：memos.db（评测记录库，纯本地）

## 1. 背景与摩擦

评测记录库 `memos.db`（test_runs / test_case_results / test_case_definitions）在 2026-09-06
移出版本控制后成为**每机一份的本地 SQLite**：开发机与服务器各跑各的评测、各存各的 run，
跨机对照只能靠人肉口头对齐——典型事故：full provider 原文直给 90% 那轮在开发机跑的，
本机库里根本没有这条记录，口径核对无从谈起（见 §6 验收的案例 1）。

同时评测是"双机协作"的：开发机跑实验 → push 代码与方案文档 → 服务器 pull 复现轮 → 对照失败集。

## 2. 目标与非目标

目标：
1. 任一侧跑完评测，run 结果（元信息 + config_snapshot + 逐 case 详情）能被另一侧**只靠 git pull 看到**；
2. 两侧最终收敛为**同一份 run 并集**，重复同步幂等（不产生重复行、不丢已存在的 run）；
3. 完全免费、无墙依赖、**不在服务器新增任何常驻服务**；
4. 保留现有工具链特性：audit_run_attribution 等继续离线只读本地库。

非目标：
- 不强一致（两侧同时查库要求秒级一致 → 那是方案 2 的事，见 §4）；
- 不同步 memories.db（提取缓存库，大文件、语义不同，单独走 rsync/scp，见 §8）。

## 3. 硬约束（决策前提）

- 服务器是国内云主机，**CF D1 / Turso / Neon 等墙外免费库直连不可靠**，排除；
- 国内大厂免费云库均为限时试用/实名任务，无个人长期免费档，不引入；
- 服务器资源紧（空闲 ~100MB），**不加常驻服务**；
- 评测记录：低频（一天几轮）、小（~100–300KB/轮）、可再生成（本地 db 可重出）、低敏感（合成用例）。

## 4. 方案选型与结论

| 方案 | 形态 | 结论 |
|---|---|---|
| 1. git 文本导出 | 每轮 run 导出不可变 JSON 入 repo，随现有 push/pull 流动 | ✅ **默认采用**：零新依赖、贴合既有双机工作流 |
| 2. 复用 datapolit-mysql8 做中心库 | 独立 database + 低权账号，3306 安全组白名单 | ⏸ 备选/演进：需要"看板双机实时可见"时启用；导出的 JSON 就是迁移介质 |
| 3. 墙外免费云库 | CF D1 / Turso / Neon | ❌ 国内连通性否决 |
| 4. 国产第三方云库 | 大厂限时免费 / 小厂实名 | ❌ 无长期可靠免费档，低价值数据不值第三方依赖 |

两方案可共存：先 1 后 2，export 文件是两者之间的事实迁移格式。

## 5. 架构与数据流

```
任一侧本地（真相）: memos.db ──export──▶ evals/runs/run_<hex>.json（不可变镜像）
                                              │ git add/commit/push（wrapper 强制）
                                              ▼
git origin（搬运通道，github 私有 repo）
                                              │ 另一侧 pull
                                              ▼
另一侧本地: run_*.json ──import（幂等收敛）──▶ memos.db = 两侧 run 并集
```

关键设计决策：
- **本地 SQLite 是真相**；JSON 只是"可再生成镜像"——git 全乱也能从任一侧 db 重出，不丢数据；
- **run_id 天然唯一**（`run_{uuid4.hex[:10]}`，conftest 生成）→ 数据层无主键冲突；
- **每轮一个不可变文件，落库后不改**（勘误走新文件/notes，不覆盖）→ git 层无文件冲突；
- **永不提交"汇总 index 文件"**（如 all_runs.json）——那是唯一会真冲突的东西，需要列表时本地脚本从 run_*.json 重建；
- 导出=运行库当前 schema 的**通用列快照**（PRAGMA 驱动），列漂移不炸。

## 6. run JSON 格式（schema_version: 1）

文件：`evals/runs/run_<id>.json`，单文件含一轮全部数据（供远端离线审计，字段即本地表列）：

```jsonc
{
  "schema_version": 1,
  "exported_at": "2026-09-07T12:00:00+08:00",   // 导出时刻（仅元信息，import 不写回）
  "run": {                                        // = test_runs 整行（含 config_snapshot 原样 JSON 文本）
    "id": "run_80f3624109", "phase": "layer1", "run_at": "...",
    "total_cases": 60, "passed_count": 14, "pass_rate": 0.7,
    "config_snapshot": "{...}", "status": "completed", "...": "其余列照搬"
  },
  "cases": [                                      // = test_case_results 整行 ×N
    { "run_id": "run_80f3624109", "case_id": "layer1_11_mortgage_application",
      "passed": 0, "score": 0.0, "actual_answer": "...", "retrieved_memories": "...", "...": "其余列照搬" }
  ]
}
```

- export 只负责搬运**运行库在导出时刻存在的列**（读 PRAGMA table_info），新列自动跟随；
- import 校验：文件列 ⊆ 本地表列 才导入，否则跳过并给出差异提示（防止未来版本回导旧版本库）；
- run_at 保持 UTC ISO 原文（与库内一致，本地时区转换是展示层的事）。

## 7. 工具接口（全部 stdlib-only，不 import os_mem/eval，任何环境可跑）

| 工具 | 命令 | 语义 |
|---|---|---|
| export | `uv run python tests/export_run.py [--run <id前缀>]` | 缺省=最新 run（rowid 序）；写 `evals/runs/run_<id>.json`，stdout 打印文件路径 |
| import | `uv run python tests/import_run.py <文件或目录/glob>` | 按 run_id 收敛进本地 memos.db：run 行 INSERT OR REPLACE；case 行先删该 run 再插（单事务），**幂等** |
| compare | `uv run python tests/compare_runs.py <A> <B>` | A/B 可为 run_id 前缀（查本地库）或 json 路径（查文件）；输出双方通过率 + 失败集 + 对称差（一侧过一侧挂的 case） |
| wrapper | `bash scripts/run_eval_record.sh <pytest 参数...>` | 跑评测（自动补 --record-db）→ export → git commit → push（失败容忍，见 §9）；退出码= pytest 退出码 |
| 既有 audit | 不变 | 仍读本地 memos.db；需要审计他侧 run 时先 import |

复现对照的标准动作（替代人肉对失败集）：
`git pull && uv run python tests/import_run.py evals/runs/ && uv run python tests/compare_runs.py <dev_run> <server_run>`

## 8. 双写冲突语义（两端都跑了评测）

场景：开发机跑出 run_A、服务器同时跑出 run_B。

1. 各自生成独立文件 → 各自 commit（文件不同，互不干扰）；
2. 后 push 者 non-fast-forward 被拒 → `git pull --rebase && git push`：**不同文件 auto-merge 干净，无冲突标记**；
3. 任一侧 pull → import → 本地 db 收敛为并集（含 A 与 B）；
4. 文件级真冲突只可能由"违反 append-only"（回头改已导出的 run 文件）引起 → 异常路径：保留双方版本、手工合一后重新导出。

补充说明：
- **memories.db（提取缓存）不在本方案内**：服务器复现轮要"同缓存"时，缓存库大、且要单写纪律，单独用 scp/rsync（评测发起方推送，复现机只收）或重提取（约 36min）解决；
- 同机"评测还没跑完就 push"不会发生：export 在 pytest 结束后执行，run 文件只在完整落库后生成。

## 9. 保障与兜底

| 风险 | 保障 |
|---|---|
| 忘了同步 | wrapper 强制：评测结束 → 导出 → commit → push 一条龙；直接 `pytest` 裸跑则不保证（文档写明，惯用 wrapper） |
| push 失败（墙/断网/github 抖动） | 本地 commit 已留 = 数据没丢只是晚到；wrapper 打印 ⚠ 提示，恢复后任意一次 push/下次 wrapper 补推 |
| github 长期不通 | 备胎通道：把 `evals/runs/` rsync/scp 到服务器（即方案 2 的通道） |
| repo 膨胀 | ~100–300KB/轮，实验密集期 ~1MB/天、年百 MB 级，私有 repo 可扛；超限后切"瘦 JSON 入 git + 全文按需拉" |
| schema 漂移 | export 通用列快照 + JSON schema_version；import 列子集校验 |
| 本地 db 损坏/误删 | 他侧 run 文件 + import 可重建（db 权威但在极端情况下镜像可兜底） |

## 10. 落地批次

- **B1 文档**：本文件（✅ 本次）
- **B2 工具**：`tests/export_run.py`、`tests/import_run.py`、`tests/compare_runs.py`、`scripts/run_eval_record.sh` + 本机真实 run 往返验证（export → import ×2 幂等 → compare 两个真实 run）
- **B3 采纳**：wrapper 成为跑评测的默认入口（README 增补用法）

## 11. 验收标准

1. 本机 export 最新 run 生成 JSON，重复 export 内容一致（同 run 快照稳定）；
2. 同一 JSON import 两次：第二次无新增、行数不变（幂等）；
3. compare 两个真实 run（如 run_80f3624109 vs run_64f82a0d1b）输出失败集差异与对称差，与手工核对一致；
4. （跨机，开发机配合）开发机跑一轮 → push → 服务器 pull + import → 服务器库出现该 run，compare 可跑。
5. 案例 1（本方案的导火索）闭合：full provider 90% 那轮若在开发机复跑并走 wrapper，服务器侧 pull 后即见其 config_snapshot 口径，无需人肉口头确认。

## 12. 未决问题（不影响 B2 落地）

- 导出粒度是否需要"瘦模式"（仅 meta + score/passed/error，不含窗口/答案全文）——先全量，膨胀到痛再切；
- export 是否在 conftest 里自动挂钩（--record-db 即导出）——先不挂，保持"评测代码不感知 git"，用 wrapper 显式驱动；
- github 私有 repo 容量政策变化时是否启用备胎通道。

## 附：机制术语学习笔记（本次设计用到的概念）

- **最终一致性（eventual consistency）**：两侧不要求同时看到同一状态，只保证"没有新写入后，经过足够同步最终相同"。适用场景=低频追加 + 有既有 pull-before-run 纪律；强一致（实时同库）才需要方案 2。
- **幂等（idempotent）**：同一操作执行 N 次与执行 1 次效果相同。import 用"run 行 replace + case 行先删该 run 再插"实现整 run 收敛幂等。
- **append-only + 不可变文件**：只新增不修改。run_id（uuid）唯一 + 每轮独立文件 + 落库后不改 ⇒ 数据层无主键冲突、git 层无文件冲突——**冲突不是靠解决，是靠设计让它不发生**。
- **INSERT OR REPLACE**：SQLite 按主键/唯一索引先删后插。配合整 run 事务删除，达到"文件是这轮的唯一事实，重放即对齐"。
- **non-fast-forward 与 rebase**：push 被拒 = 远端有新提交本地没有；`pull --rebase` 把本地提交重放到远端头上，不同文件自动合并。merge 冲突标记只出现在同文件同区域被双改——本方案已按文件隔离消除。
- **镜像可重建（reproducible artifact）**：导出 JSON 不是唯一副本，可从本地 db 重新生成——降低对传输通道可靠性的要求（丢了就重导）。
- **行级真相 vs 库级真相**：本地库行是权威；git 里是"别人库的行搬到我这的传输格式"，import 完成收敛后本地库才可审计。
