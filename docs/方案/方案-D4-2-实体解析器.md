## 1. 问题实证

### 1.1 现状：实体维度是死的

主方案的签名已升级为 `(entity_ref, attribute, lifecycle)`，但 `extractor/utils/normalize.py`
的 `resolve_entity()` 长期是**占位实现——一律返回 `SELF`**。于是**所有主体的属性全挤在同一个 `SELF` 上**。

### 1.2 实证一：17 条「完全消失」（layer1 全量审计）

兜底句被 R1 剪掉、但其精确 token 在**最终落库的结构化事实**里也找不到：

```
兜底句 537 条 → 落库 159 → 被剪 378，其中 17 条属静默丢失，横跨 8 例
```

| 用例 | 丢失的信息 |
|---|---|
| 02 保险 | `ENT-7739482` 租赁确认号；`916-555-2234` / `916-555-8899` |
| 05 网络开户 | **`VEL-89923476` ×3** |
| 08 酒店 | 12月9日 7:30 PM（Vela） |
| 10 药房 | Jardiance 的 `$47` 共付额 |
| 11 房贷 | Vanguard `$125,000` / TD Ameritrade `$38,000`；401k `$285,000` / Roth IRA `$78,000`；Visa `$2,300` / Amex `$1,100`；额度 `$15,000`/`$12,000`/`$25,000` |
| 14 手机 | `$90` 套餐 + `$15` 保险 = `$105` |
| 15 选课 | **`MAT-151` 的 MWF 8:00-9:15 AM** |
| 20 日托 | `$200` 年度材料费 |

**根因链**（以 05 为例）：两条 `account_number` 分属不同主体（Velocity 宽带账户 / Chase 银行账户），
却归一到同一签名 → 批内收敛静默丢弃一条 → R1 又拿「LLM 原始输出」当覆盖判据，
把 3 条含 VEL 号的兜底句一并剪掉 → **结构化与兜底双保险同时失效，信息凭空消失且无痕**
（无 superseded 行、无 previous_fact、无日志）。

### 1.3 实证二：85 条「结构化被丢」（Fix C 上线后量化）

修复 v1 后重提取（run_452ba69d36），新加的收敛告警暴露出更大的量：

```
批内同签名收敛丢弃 85 条结构化事实，20/20 例全部中招
11 房贷 -13   03 医疗 -14   13 税务 -8   04 航线 -7   02 保险 -6   10 药房 -6 …
```

**Fix B 只能救回"同时有兜底句"的数字类**；像 `User's dog is named Max`（17）、
`User's wedding has 150 guests`（19）、`User's full name is …` 这类**没有数字 → 不产生兜底句 → 真的丢了**。

> ⚠️ **「审计归零」≠「零缺失」**：审计只覆盖有兜底句可对照的那一半。上一轮验证的 17→0
> 是**判定更严的那个子集**归零，不是全部丢失归零。

### 1.4 根因判断：**单值假设** + **单一实体**

批内同签名收敛隐含一个假设：**每个 (实体, 属性) 只有一个当前值**——即"**单值属性**"。

但很多属性天然**多值**：药物、症状、课程、信用卡、人物。真正缺的不是"属性要多值"，
而是——**实体维度只有一个取值（SELF）**，于是把"多个主体各自的单值"误当成"一个主体的多值"，
只能留一条。

> `dosage` 永远是单值的——但它是"**每种药各自的**单值"。

## 2. 术语与设计总览

一条事实的完整语义 = **（谁的）（什么性质）=（什么值）**，加上"当前还是历史"。四个概念各司其职：

| 概念 | 承载 | 回答的问题 |
|---|---|---|
| `attribute` | 规范属性名 | **什么性质**（medication / wire_amount / closing_date） |
| `entity_ref` | 实体标识 | **是谁 / 哪个实例**（SELF、`ID:VEL`、`DRUG:甲氨蝶呤`、`CARD:visa`） |
| `lifecycle` | current / historical / superseded | **当前值还是历史快照** |
| **属性策略**（本文新增） | functional / multi_valued | **值是否承担"实例标识"职责** |

**核心原则**：**维度归维度，来源归来源。**
实例一律进 `entity_ref`（维度统一）；而"实例名从哪来"允许多路来源（见 §3）。

## 3. 实体线索：四条来源与优先级

`resolve_entity(fact, category, canonical_attribute, key, value, policy) -> str`

| 优先级 | 来源 | 规则 | 例 | 状态 |
|---|---|---|---|---|
| **P0** | 形式化编号 | `\b[A-Z][A-Z0-9]{1,7}-\d{2,}\b` | `VEL-89923476` → `ID:VEL`；`ENT-7739482` → `ID:ENT` | ✅ v1 |
| **P1** | 产品/课程码 | 同上且 category ∈ {education, work, product, subscription} | `MAT-151` → `PROD:MAT-151` | ✅ v1 |
| **P3** | 多值属性 + **key 内实例名剥离** | key 形如 `<属性>_<实例名>`（长前缀优先） | `medication_atorvastatin` → `DRUG:atorvastatin`；`medication_甲氨蝶呤` → `DRUG:甲氨蝶呤` | ✅ v2 |
| **P3a** | 多值属性 + **专名抽取** | 文本中**恰好命中一个**专名（按词剔停用词） | `The Visa has a $2,300 balance` → `CARD:visa` | ✅ v2 |
| **兜底** | 都拿不到 | — | `SELF`（= 现状，**绝不会更差**） | ✅ |

**优先级理由**：形式化线索是**零误伤**的硬标识，先判；**专名线索中"显式优于推断"**——
LLM 明确写在 key 里的实例名（P3）比从文本猜（P3a）可靠，故 P3 排在 P3a 前。
同一事实命中多条时取最高优先级。

> 编号 P2 已并回 P3a：原文档把"专名抽取"标为 P2（早于 P3），实施后确认
> **显式线索应优先于推断线索**，故调整为 P3 → P3a。

### 3.1 P3：key 内实例名剥离（中文场景的关键路径）

`extract_instance` 依赖大小写线索，**中文事实无此线索**（`用户服用甲氨蝶呤` 里没有确定性标记）。
因此允许 LLM 在 key 里携带实例名，由**系统**剥离并放进实体维度：

```
LLM 输出 key = "medication_甲氨蝶呤"
  → 属性策略查得 (health, medication) = multi_valued
  → 剥离前缀 "medication_" → 实例名 "甲氨蝶呤"
  → entity_ref = "DRUG:甲氨蝶呤"，attribute = "medication"（稳定属性）
```

**关键**：LLM 只提供**字符串**（它擅长的），**系统决定这个字符串放在哪个维度**（裁决规则仍是确定性代码）
——符合红线。这也是主方案 §4「`entity_hint`：只是提示，不是权威」的落地形态。

剥离规则（`_instance_from_key`）：

1. `key` 以 `<multi_valued 属性>_` 开头且剩余部分非空 → 剩余部分为实例名；
2. **长前缀优先**（`course_schedule_math101` 不能被 `course_` 先吞掉）；
3. 剩余部分若本身是**生命周期词**（`current`/`original`…）→ **不剥离**（防误吞）；
4. 剥离**先于** alias 表查询（alias 表不认识带实例后缀的 key）；剥离后属性归到稳定属性。

### 3.2 P3a：专名抽取（`_instance_from_text`）

确定性规则，无词表、无 LLM，**仅对 `multi_valued` 属性生效**：

1. 在 `fact` / `value` 中匹配**首字母大写的连续词组**（`[A-Z][a-zA-Z]{2,}(?:\s+[A-Z][a-zA-Z]{2,})*`）；
2. **按词**剔除停用词（`The Visa` → `Visa`；`The User` → 空 → 整条跳过）；
3. 归一（小写、去标点（保留中日韩）、空白折叠、限长 40）；
4. 命中**恰好一个** → `"<TYPE>:<归一实例名>"`；**命中零个或多个 → 返回 None**（保守）。

> **实测边界**：P3a 对"一句多主体"（`The Visa has $2,300, MasterCard paid off, Amex $1,100`）
> 会命中 3 个 → 保守回退 `SELF`；对中文（无大小写）完全失效。
> 前者需**拆句**另立项，后者由 **P3** 覆盖。

## 4. 属性策略（functional / multi_valued）

### 4.1 声明形式：数据，不是代码

仿现有 `fact_category` / `fact_key` 受控词表的模式，新增一张策略表：

```
(category, attribute) → functional | multi_valued      # 缺省 functional
```

**缺省 `functional` ⇒ 行为与现状逐字节一致，零回归。** 词表可管理演进，后续可由 L3 离线聚类补充。

### 4.2 白名单：**只收实证确认的**（按用例逐步补）

首批只开**三个用例**实证涉及的属性（用户 2026-09-12 定：「属性策略先用三个用例跑」）：

| category | attribute | 判定依据 | 实证强度 |
|---|---|---|---|
| health | `medication` | **03 医疗**：`atorvastatin 20mg` 被批内收敛丢弃（lisinopril 存活）→ 两药并存被误判为"同一属性的两个值" | **实证确认** |
| education | `course_schedule` | **15 选课**：`Psychology 101`（无连字符编号）落在 `SELF`，与 `PROD:MAT-151` 等不同实体 | 强 |
| education | `course_registration` | 15 选课同上 | 强 |
| education | `course` | 15 选课（兜底基名） | 中 |
| finance | `credit_card` | **11 房贷**：Visa / MasterCard / Amex 三张卡 | 中（该例丢弃样本多为**同事实换个说法**，见 §4.2.1） |
| finance | `investment_account` | 11 房贷：Vanguard / TD / 401k / Roth 并存 | 中 |
| finance | `bank_account` | 11 房贷：Wells Fargo / Marcus | 中 |

**未纳入首批**（有嫌疑但**无实证**，等复测再定）：`health/symptom`、`health/allergy`、
`education/recitation_section`、`education/meal_plan`、`personal/person`。

> **刻意窄开**：白名单越宽，把"更新"误判为"并列"（→ 冗余）的风险越大。
> 先窄开跑通，再按审计数据逐步扩——比一次铺开再回滚便宜。

#### 4.2.1 附：实测发现——批内收敛**不全是坏事**

11 房贷的丢弃样本与库中存活事实对照后确认：**样本多数是"同一事实换个说法"的合法去重**：

| 被丢弃 | 库中存活 | 性质 |
|---|---|---|
| `planned closing date is January 15th, 2025` | `closing_date is January 15th` | **同事实**（去重正确） |
| `down payment is entirely from their own savings` | `down_payment_gift`：同内容 | **同事实**（去重正确） |
| `down payment funds will come from Wells Fargo and Marcus` | `down_payment_source`：同内容 | **同事实**（去重正确） |
| `User takes atorvastatin 20mg at night`（03） | 无对应行 | **真丢失** ❌ |

**结论修正**：「85 条批内收敛丢弃」中**有相当比例是合法去重**，不等于 85 条真丢失。
要区分二者，需在复测时**放开收敛样本上限**（v2 已把 `collapsed_samples` 上限调到 20）逐条对照。
**真丢失的特征是：被丢弃事实在库中找不到语义等价行。**

### 4.3 判定原则：**并列** 还是 **更新**？

两者外观相同（同属性多个值），语义相反，必须逐个实测判定：

| 用例 | 现象 | 判定 |
|---|---|---|
| 02 保险：`916-555-2234` → `916-555-8899` | 用户**更换**了号码 | **functional**（更新，走版本链） |
| 11 房贷：Visa / MasterCard / Amex 三张卡 | 三张卡**同时存在** | **multi_valued**（并列，各成实体） |

> 判错的代价不对称：把"并列"误判为 functional → **丢失**；把"更新"误判为 multi_valued →
> 同属性下多一条并存的旧值（**冗余**，可后续收敛）。**宁可冗余，不可丢失**（见 §6）。

## 5. 关键设计点：如何区分「多值并列」与「版本演进」

这是整个方案的安全阀，答案是**按属性策略分工**：

| 属性策略 | 是否切分实体 | 版本演进（同一实例的值演进） |
|---|---|---|
| **functional** | **绝不切** → 恒 `SELF` | ✅ 完整保留（`$85k→$100k→$95k` 走 as-of 裁决） |
| **multi_valued** + 抽到实例名 | 按实例切 | ✅ 同一实例内仍走版本链（甲氨蝶呤 15mg→20mg） |
| **multi_valued** + 抽不到实例名 | **回落 `SELF`** | ✅ 退回现状（最多还是丢，不会更差） |

**例**（同一份库里同时成立）：

```
(DRUG:methotrexate, medication, current) = 甲氨蝶呤 15mg
(DRUG:cbd,          medication, current) = CBD 油 10mg        ← 三药并存
(DRUG:prednisone,   medication, current) = 泼尼松 每日两次
(DRUG:methotrexate, medication, …)       = 甲氨蝶呤 20mg      ← 同实体 → 版本演进 ✅
(SELF,              wire_amount, current) = $95,000           ← 单值，不切
```

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| **值归一不稳定**（`Methotrexate` vs `MTX` 裂成两个实例） | 接受——**裂开 = 同属性下多一条 current（冗余）；丢失 = 不可逆**。裂开可后续用 alias/L3 聚类收敛 |
| **属性策略误判**（把"更新"判成"并列"） | 误判只产生冗余不产生丢失（§4.3）；白名单从实测逐条补，不预先扩张 |
| **专名抽取误切**（把普通词当实例） | 停用词表 + "恰好命中一个"才切 + 仅限 multi_valued 属性；拿不准一律 SELF |
| **中文场景 P2 失效** | 由 P3（key 内实例名剥离）兜住 |
| 实例名依赖 LLM key（P3） | 仅作 P2 之后的补充；P3 抽不到仍回落 SELF |
| 存量数据 | 不改已有行；新签名只影响新提取。必要时按 user 重建投影 |

## 9. 非目标

- **一句多实体**（单条 fact 内并列多主体，如 `The Visa has $2,300, MasterCard paid off, Amex $1,100`）
  → 需**拆句**，属提取粒度问题，D4-2 与 Fix B 都管不到，另立项；
- 全局实体知识库 / 实体消义大模型；跨用户共享实体。

## 10. 被否方案

| 方案 | 否决理由 |
|---|---|
| **拆属性**（实例进属性名，如 `medication.methotrexate`） | ① **命名漂移责任仍留在 LLM**——每个实例都要它稳定拼对属性名（主方案 §8.2 已实证静态 alias 追不上临场漂移）；② 别名表 **O(实例数 × 表述数)** 持续膨胀；③ 与 P0/P1 已有的实体维度形成**双重标准**；④ 取"全部药物"依赖属性名前缀可枚举，漂移一发生就扫不到。**唯一优势**：不依赖专名抽取，中文场景更稳——已用 **P3（key 内实例名剥离）** 吸收 |
| **纯专名注册表**（从既有事实预建实体表） | 首轮会话实体尚未注册 → 命中不了 → 回退 SELF；而首轮恰恰最需要它 |
| **LLM 输出权威 `entity`** | 违反红线（裁决不靠模型推理）。仅允许其提供**字符串**（P3），裁决仍由系统确定性完成 |
| **批内不收敛、允许多条 current** | 不解决根本：投影键仍相同 → 检索侧 `StructuredKeyDedup` 照样折叠成一条，问题只是被推到了下游 |
| 按"值"无差别做实体键 | 会把**版本演进**（`$85k→$100k→$95k`）切成多个实体、毁掉版本链。必须**按属性策略**限定作用域 |

## 附录：业界机制对照

- **RDF / 知识图谱**：三元组 `(subject, predicate, object)` 与本文 `(entity, attribute, value)` 同构；
  `entity_ref` 即 subject，`attribute` 即 predicate。多值属性在 RDF 里天然成立（同一 subject+predicate
  可有多个 object）——本项目受限于"每签名一条 current"的收敛模型，故需把实例升为 subject（实体）。
- **关系数据库的多值属性**：标准做法是把多值属性拆成**子表**（`medications(user_id, drug_name, dose)`），
  即"实例升为一行/一个键"。本文的 `entity_ref = DRUG:<药名>` 等价于该子表的主键片段。
- **函数依赖（functional dependency）**：单值属性 = 满足 `(entity, attribute) → value` 的函数依赖；
  多值属性违反该依赖，故不能共用同一收敛键——这与数据库范式理论中"多值依赖需独立关系"一致。
- **实体链接（entity linking）**：业界通常靠模型做实体消义；本项目红线要求确定性，
  故采用"形式化线索优先 + 保守回退"，把不确定性转化为**冗余而非丢失**。
