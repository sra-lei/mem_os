# D4-2 方案：确定性实体解析器（entity_ref）

> 状态：**v1 已实施**（2026-09-12）：E1 编号前缀 + E4 产品/课程码 + 投影收敛键
> （`projection_key`，SELF 保持裸 attribute 零迁移）；**E2 机构名 / E3 人名延期**
> （需注册表词表证据，且存在误切本人事实的风险——见 §3.3）。单测
> `tests/unit/test_d4_entity.py` 19 例；审计脚本 `scripts/audit_silent_loss.py`。
> 上游：`docs/方案/方案-D4-实体归属与as-of版本裁决.md`（D4-0/1/3 已实施，D4-4 已回放验证）
> 红线（用户 2026-09-09 定）：**裁决逻辑必须是确定性系统代码，不依赖 LLM 运行时推理**
> 关联证据：本文件 §2 的 17 条静默丢失扫描（`scripts/audit_silent_loss.py`）

---

## 1. 现状

`extractor/utils/normalize.py` 里 `normalize_key()` 已产出 `(entity_ref, attribute, lifecycle)`，
但 `resolve_entity()` 是**占位实现——一律返回 `SELF_ENTITY`**。因此
「同一 attribute 下的多实体并存」全部撞进同一个签名 `(SELF, attribute, current)`。

落库裁决 `plan_versioning` 对**批内同签名**做收敛（保留 `source_started_at` 最新者；
同一会话内时间戳全部并列 → 实测 `_is_newer(t, t)=False` → **保留先出现的那条**），
被丢弃者**无 superseded 行、无 previous_fact、无日志**——静默消失。

## 2. 问题实证：17 条静默丢失（layer1 全量扫描，零 LLM）

扫描原理：兜底句被 R1 剪掉、但其精确 token 在**最终落库的结构化事实**里找不到
→ 该信息在库中彻底消失（既无结构化、也无兜底）。

```
兜底句 537 条 → 落库 159 → 被剪 378，其中 17 条属静默丢失，横跨 8 例
```

| 用例 | 丢失的信息 |
|---|---|
| 02 保险 | `ENT-7739482` 租赁确认号；`916-555-2234` / `916-555-8899` |
| 05 网络开户 | **`VEL-89923476` ×3** |
| 08 酒店 | 12月9日 7:30 PM（Vela） |
| 10 药房 | Jardiance 的 `$47` 共付额 |
| 11 房贷 | `$125,000` Vanguard / `$38,000` TD Ameritrade；`$285,000` 401k / `$78,000` Roth IRA；Visa `$2,300` / Amex `$1,100`；额度 `$15,000`/`$12,000`/`$25,000` |
| 14 手机 | `$90` 套餐 + `$15` 保险 = `$105` |
| 15 选课 | **`MAT-151` 的 MWF 8:00-9:15 AM** |
| 20 日托 | `$200` 年度材料费 |

**根因链（05 为例，四步全部有证据）**
1. `User's account number is VEL-89923476`（Velocity 宽带账户）与
   `User's checking account number is 8829447651`（Chase 银行账户）**归一到同一签名**
   `('SELF','account_number','current')`——两条本是**不同实体**的属性；
2. 批内同签名收敛 → 丢弃后者之前的那条，静默；
3. R1 剪枝的判据是「LLM 原始输出」而非「实际将落库的事实集」：
   收敛后被丢的那条仍出现在 `structured_tokens` 里 → 连带把 3 条含 `VEL-89923476`
   的兜底句也剪掉（复现：用收敛前视图 0/3 保留，用收敛后视图 3/3 保留）；
4. **双保险同时失效** → 信息凭空消失。

> 该扫描是**下限**：LLM 结构化事实被收敛丢弃、且无兜底句可对照的，扫描看不见。

## 3. 设计：实体线索 → entity_ref（四类，按精度排序）

解析器 `resolve_entity(fact, category, key, value, *, registry) -> str`，**纯函数、可单测**。

| # | 线索 | 规则 | entity_ref | 例 |
|---|---|---|---|---|
| E1 | **编号前缀** | `fact`/`value` 命中 `\b[A-Z]{2,}-\d{2,}` → 取前缀 | `ID:<PREFIX>` | `VEL-89923476` → `ID:VEL`；`ENT-7739482` → `ID:ENT` |
| E2 | **机构名** | 命中本 user 的机构注册表，**且只命中一个** | `ORG:<name>` | `... at Fidelity` → `ORG:Fidelity` |
| E3 | **人名** | 命中本 user 的人名注册表，**且只命中一个** | `PERSON:<name>` | `Jennifer's flight` → `PERSON:Jennifer Walsh` |
| E4 | **产品/课程码** | `[A-Z]{2,}-\d{3,}` 形态且 category ∈ {education, work, …} | `PROD:<code>` | `MAT-151` → `PROD:MAT-151` |

**回退（保守优先）**：无线索 / 命中多个实体 / 解析异常 → **`SELF`**（= 现状行为，不会更差）。

### 3.3 v1 实施范围（2026-09-12）

**已实施 E1 + E4**（形式化线索，零词表、零误伤）：

| 线索 | 形态 | entity_ref |
|---|---|---|
| E1 编号前缀 | `\b[A-Z][A-Z0-9]{1,7}-\d{2,}\b` | `ID:<前缀>` |
| E4 产品/课程码 | 同上且 category ∈ {education, work, product, subscription} | `PROD:<码>` |

**延期 E2 机构名 / E3 人名**，原因：
1. 需要注册表词表（从既有事实里收专有名词），**首轮会话实体尚未注册 → 命中不了 → 回退 SELF**，
   对「首次出现即冲突」的场景无效；
2. 误切风险实在：注册表可能把用户**本人姓名**当实体 → 把本人事实切到 `PERSON:<本人>` 下，
   **直接破坏 SELF 的版本链**（比现状更差）；
3. E1/E4 已覆盖 17 条静默丢失中「编号/课程码」形态的部分（05 的 `VEL-89923476`、15 的 `MAT-151` 等），
   且零误伤——先拿到确定收益，剩余场景由 **Fix B（R1 判据对齐落库集）** 兜住更划算。

> 保留 E2/E3 的接入点：`resolve_entity(fact, category, key, value)` 是唯一入口，
> 后续按用例证据补注册表即可，不影响已落地的 W1-W4 接线。

**注册表来源（确定性构建，本地 SQLite 读，无 LLM）**
- 人名：本 user 既有 `personal` / `family` 类事实里的姓名（`full_name`、家庭成员等）；
- 机构：本 user 既有事实文本中的专有名词（首字母大写词组 / 全大写缩写），
  减去停用词表（`User`/`The`/`SELF`/月份/星期/常见动词…）；
- 前缀 / 产品码：正则直取，无需注册表。

### 3.1 红线：**绝不用「值」做实体键**

`$85,000 → $100,000 → $95,000` 是**同一实体的版本演进**，必须仍归 `SELF` + 同签名，
由 as-of 版本裁决收敛。只允许「事实文本里**显式命名**的实体线索」触发切分。
违反此条会把版本链切成多个实体，破坏 D4-1/D4-3 已有成果。

### 3.2 非目标（本阶段不做）

- 一句多实体（`The Visa has $2,300, MasterCard paid off, Amex $1,100`）→ 退回 `SELF`；
  拆句属提取粒度问题，另立项；
- 不做实体消义大模型 / 全局实体库；不做跨用户实体。

## 4. 接线：不止改 `resolve_entity`（三处必须同步）

| # | 位置 | 现状 | 改为 |
|---|---|---|---|
| W1 | `normalize.py::normalize_key` | `entity_ref=SELF_ENTITY` 写死 | 接 `resolve_entity(...)`，签名扩参传入 fact/value + registry |
| W2 | `struc_mem_service` 投影**删旧** | 按 `(category, attribute)` 删（L272-277） | 按 `(category, entity_ref, attribute)` 删 |
| W3 | 投影**回读/写入键** | `wanted={(cat, attr)}`；投影 `key=attribute`（L266/296） | 投影 `key` 带上实体（如 `f"{entity_ref}:{attribute}"`），wanted 同改 |
| W4 | 检索侧 `StructuredKeyDedup` | 按 `(category, key)` 去重 | 因 W3 已让 key 携带实体，**自动生效**，需补单测锁定 |

> ⚠️ **W2/W3 是必须项**：只改 W1 会让两个实体的同名 attribute 在 Milvus 投影里
> 互相删除、并在检索去重时被折叠成一条——存储层留住了事实，注入窗口仍然只看到一个。

## 5. 验收与验证

**单测（新增，`tests/unit/test_d4_entity.py`）**
1. E1-E4 四类线索各自切分出独立签名；
2. **版本演进不被切**：`wire_amount` 的 `$85k→$100k→$95k` 三批入库后仍同签名、
   current=$95k 且版本链完整（回归 D4-1 行为）；
3. 命中多个实体 → `SELF`；无任何线索 → `SELF`；注册表为空 → `SELF`；
4. W3 投影键：两实体同名 attribute → 投影两条、互不删。

**集成验证**
5. 静默丢失扫描固化为 `scripts/audit_silent_loss.py`（纯确定性、零 LLM）：
   修复前 17 条 → 目标显著下降（预期覆盖 05/10/11/15 类）；
6. layer1 端到端**不回退**（当前 13/20）；211 单测绿；
7. 按纪律：层1 定向复测（受影响用例 05/11/15/20）或全量，须用户确认参数后跑。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 误切（同一实体的不同表述被切成两个实体 → 版本链断裂） | 只在显式线索命中时切；红线 §3.1；命中多个一律 SELF |
| 注册表误收（把普通词当机构名） | 停用词表 + 只收本 user 事实中反复出现的专有名词；命中多 → SELF |
| 注册表为空（新用户首轮） | 回退 SELF = 现状，不更差 |
| 投影键变更引入脏向量 | 变更后需重建该 user 投影（`scripts/` 提供重建入口）；审计脚本核验 |
| 静默丢失仍存在于一句多实体场景 | 由 **Fix B（R1 判据对齐实际落库集）** 兜住——见 §7 |

## 7. 与 Fix B 的关系（建议同批做）

- **D4-2（本方案）**：让多实体的**结构化事实不再被误覆盖**；
- **Fix B**：让 **R1 不再拿「未落库的事实」当覆盖依据**（把批内同签名收敛提前到 R1 之前，
  或用收敛后的视图做判据）→ 兜底句保住信息，覆盖一句多实体等 D4-2 管不到的场景；
- **Fix C（零风险）**：批内收敛加计数 + WARNING 日志，让同类丢失可观测。

三者互补，各自独立 commit；D4-2 是**治本**，Fix B/C 是**保险**。
