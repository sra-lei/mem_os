## 一、问题与背景

### 1.1 现行实现（2026-09-12 现状）

```
struc_mem_service.get_structured_memories
  └─ fetch = top_k × RETRIEVAL_FETCH_MULTIPLIER(=3)          ← 放大取回
  └─ vec_storage.search：dense(COSINE) + sparse(BM25) 融合      ← RRF 默认 / dense_lead 可选
       └─ per_route = fetch × 2                                  ← 第三层倍数嵌套
  └─ apply_retrieval_strategies 策略链（固定 5 段，无开关）：
       VerbatimNoiseFilter → StructuredKeyDedup → RedundantVerbatimFilter
       → VerbatimQuota → StructuredQuota → 终装配（结构化在前、verbatim 补位，截断 top_k）
```

这套链的原始目标是 **覆盖漏**（库里有、没进注入窗口）。当时的证据（
`方案-检索注入verbatim区分策略.md` §一，run_7979 逐 case 复核）：

```
期望点缺失合计 = 提取漏 3 : 覆盖漏 26 : 回答漏 3
→ "当前瓶颈不在记太多，而在注入窗口对『结构化未覆盖、仅 verbatim 承载的信息』不可及"
```

链的两轮实测收益（同库、judge=assert、top_k=15 不变）：

| 轮次 | 覆盖漏 | 通过 |
|---|---|---|
| 基线（旧策略：结构化优先 + verbatim ≤1/3） | 30 | 11/20 |
| 策略链 v1/v2（区分准入 + 双配额） | 18 | **14/20** |

### 1.2 归因修正：链治的是覆盖漏，不是提取漏

必须把两个概念分开，因为它们对应完全不同的解法：

| 缺失层 | 含义 | 解法 | 现状 |
|---|---|---|---|
| **提取漏** | 库里根本没有该信息 | 入库侧：verbatim 兜底（`regular_extractor.fallback_numeric_facts`）+ R1 剪枝 + D4 归一/裁决 | 已大幅收敛：判分数值 token 的**库内可达率 95%**（本方案 §六实测），残余是派生合计值（如 case 11 的 `$130,500`），检索侧永远修不了 |
| **覆盖漏** | 库里有，没进注入窗 | **检索注入侧** ← 本方案的战场 | 现链 k=15 下判分 token 覆盖仅 **64%** |
| 回答漏 | 进窗了但没答对 | 答案侧（prompt/模型/注意力） | k=15→30 时上升，见 §1.3 |

原方案 §三 也明确论证过"优先做注入侧而非提取侧"，理由是提取侧改动必须清缓存全量重跑（成本最高）。
所以准确表述是：**链是"固定窄窗稀缺"下的资源分配补丁**——不是提取漏的解药。

### 1.3 关键实测：窗口杠杆远强于链杠杆

| 杠杆（同库同 judge=assert，仅单变量） | 覆盖漏 | 通过 |
|---|---|---|
| 基线 k=15，旧策略 | 30 | 11/20 |
| 策略链，k 仍=15 | 18 | 14/20 |
| **k=15 → 30，链不变** | **5** | **16/20** |

窗口杠杆（30→18→5）比链杠杆（30→18）强一个量级。**同一对照里出现反向指标**：
回答漏上升（03 的确认号在窗内出现两次仍漏答 0.0、13 窗内有值未答 3 点、16 的 `$36,250` 同理）
——即"加窗降覆盖漏、升回答漏"，净收益 +2 例。这条是本方案唯一必须盯住的代价，且它**不是 token 成本**。

### 1.4 链上组件的实测工作面（本机 D4 口径库：933 行 / 20 user）

| 组件 | 存在的理由 | 实测工作面 | 判定 |
|---|---|---|---|
| ×3 放大取回 | 给去重/配额留候选 | 窗=取回量时失去意义 | 可删 |
| 2 号 `StructuredKeyDedup` | 同槽多版本 / Milvus 累积重复向量 | `(category, 投影键)` 重复组 **0**（签名唯一性不变量成立；投影按 D4 键删旧插新） | **已 no-op** |
| 3 号 `RedundantVerbatimFilter` | 同值 verbatim 冗余 | verbatim token ⊆ 结构化 **0/157**（入库侧 R1 用同一 `fact_tokens` 已前置吸收）；残留仅 verbatim 之间同 token 集 **6 条** | **近似 no-op** |
| 4/5 号双配额 | 在 15 个槽里分结构化/verbatim | 不截断就没有"槽"可分配 | 可删 |
| 1 号 `VerbatimNoiseFilter` | 剔除形式干扰句（问句 / 口语碎片 / 比较调整句） | 命中 18/157；13 条真丢失里 **12 条是判分明确不想要的干扰值**，唯一误伤 = case 16 的 `$1,800` | **保留（见 §五）** |

注：2 号 的键空间是 **Milvus 投影键**（`projection_key(entity_ref, attribute)`），不是 SQLite 的
`key` 列——41 行两者不同。这一点决定了 2 号 不会误杀 D4-2 的多实例行（3 张卡额度、5 门课），
但它因此也真的没有活干。D4-2 的 `projection_key` docstring 里已写明该设计正是为了避开
"被检索侧 (category,key) 去重折叠成一条"。

## 二、术语

| 词 | 含义 |
|---|---|
| 注入窗口 | 本次 query 拼进答案 prompt 的记忆条目集合（现行 `- {fact}` 逐行，上限 top_k） |
| 覆盖漏 | 期望信息在库内、但未进窗口 |
| 提取漏 | 期望信息库内不存在 |
| 神谕覆盖 | 只用库内全部行能达到的覆盖上限（任何检索策略的天花板） |
| 形式干扰句 | 形态上像"被确认过的近似值/未采纳方案"的句子（问句、`instead of`/`rather than`），实测 18 条 |
| 判分 token | `evaluation_criteria` 里的精确信息 token（口径 = `fact_tokens`，与 R1/判分器同源） |
| 全入 | 不做条数截断、不做去重/配额，把该 user 的检索结果（本例≈全部行）整体入窗 |

## 三、决策（拟）

**把"窗口内资源分配"整套机制换成"窗口放开 + 一道质量闸门 + 预算护栏"**：

1. **删** 2 号 `StructuredKeyDedup`、3 号 `RedundantVerbatimFilter`、4 号 `VerbatimQuota`、
   5 号 `StructuredQuota`（实测 no-op / 失去对象）。
2. **删** `RETRIEVAL_FETCH_MULTIPLIER`（放大取回）：检索 `limit` 直接等于预算内的条数，
   不再"放大再收敛"。
3. **保留** 1 号 `VerbatimNoiseFilter` 作为唯一质量闸门，并按其自身实测收窄（§五）。
4. **注入分区**：结构化事实在前、原文片段另起一段并标注来源性质；现状 `struct_provider.retrieve`
   是扁平 `- {fact}`，事实与原文句不可区分——宽窗下这是放大器。
5. **预算护栏**：`k` 的语义从"条数"改为**token 预算**（默认全入）。超预算才回退排序截断，
   为 layer2/3 多会话累积留退路（本机无 layer2 数据，见 §八）。

保留 `dense + sparse` 双路检索本身（与融合模式 rrf/dense_lead 的取值无关）：它是召回手段，
不是窗口分配策略。

## 四、为什么这样切：稀缺消失 → 分配器失效

- 现行链的每一段都在回答"15 个槽给谁"：2 号去重（腾槽）、3 号剔冗余（腾槽）、
  4/5 号配额（分槽）。**窗口放开后没有槽，这四段没有对象**。
- 反向看：链当年唯一被证明有效的一步，是**在固定 15 槽内把 verbatim 载体放进来**
  （case 17/18/20 恢复，11/20→14/20）。宽窗让"结构化事实"和"verbatim 载体"同时入窗，
  这一步的价值自动兑现，不需要再靠配额博弈。
- 唯一不属于"稀缺"问题的是 1 号：它治的是**正确性**（把"被确认过的近似值/未采纳方案"送进
  上下文，会诱导答案给出错值）。窗越宽，这类句子进上下文的概率越大，所以 1 号
  **越该留而不是越该删**。

## 五、1 号的处置（本方案里唯一需要保留判断的组件）

### 5.1 立论前提已失效一半（本轮新发现）

1 号 的比较句分支注释举的样例是 case 20 的 `$308.75 instead of $617.50 for that week`。实测：

- 该 verbatim 句**已不在库中**（18 条命中里没有它）；
- 同内容现在以**结构化事实**形式存在并存进窗口：
  `key=vacation_week_tuition`（"User's vacation week tuition would be $308.75 instead of $617.50"）、
  `key=vacation_tuition`。

而 1 号 只对 `verbatim_*` 行生效 → **它对这条原始目标已经拦不住了**。更要注意：这暴露一个格式问题——
同一句"比较型中间值"以结构化事实进入注入时，链上没有任何闸门。

### 5.2 收窄改法（待确认）

| 子判据 | 实测 | 建议 |
|---|---|---|
| 口语碎片 `^(yes\|okay\|…)$` | **0 命中**；且 verbatim 行按构造必含精确 token（`regular_extractor` 只收含 `_NUMERIC_TOKENS` 的句子），该分支结构上不可达 | **删除**（零行为变化） |
| 问号结尾 | 14 命中；10 条真丢失但**全部**是判分不想要的干扰值（旧电话/近似合计/错误猜测）；安全性依赖"同值有声明句孪生"（case 06 卡号即此例） | **保留** |
| `instead of` / `rather than` | 5 命中；唯一误伤 case 16 的 `$1,800`（判分点名要的"saved $1,800"调整项）；立论样例如 §5.1 已失效 | 二选一：**收窄为"句内已含被覆盖 token 才判噪"**（保住 `$1,800`）或 **直接删**（理由：目标样例已失效，且同内容现在走结构化路径不受它管辖） |

## 六、离线对照（本机实测，2026-09-12）

脚本：`scripts/compare_injection_modes.py`（只读，不接 LLM、不连 Milvus）。
基准 run：`run_79fd83b0ba`（2026-09-12 D4 口径重跑，struct/assert/top_k=15，12/20）。
判分 token 口径：`test_case_definitions.evaluation_criteria` × `fact_tokens`。

三种模式：

- **A 现链**：该 run 落库的真实 `retrieved_memories`（真实 RRF 排序 + 现链，top_k=15）
- **B 全入 + 1 号闸门**：库内该 user 全部行，verbatim 段先过生产 `VerbatimNoiseFilter`
- **C 全入原样**：不加任何过滤

| 指标（20 例合计 / 均值） | A 现链 | B 全入+闸门 | C 全入原样 |
|---|---|---|---|
| 窗口字符 | 20,225（1,011/例） | 54,536（2,727/例，**2.70×**） | 同 B |
| 条目行数 | 300（15/例，受 top_k 截断） | 915（46/例） | 同 B |
| **判分 token 覆盖** | **85/132 = 64%** | **126/132 = 95%** | 127/132 |
| 形式干扰句进入窗口 | 0 条 verbatim（见下注） | **0 条** | **18 条** |
| tokens 估算（run 实测回归 `tokens_input ≈ 299 + 0.241×字符`） | 542/例 | 954/例（**+413，+76%**） | 同 B |

**B 相对 A 新增覆盖 41 个判分 token，分布在 9 个 case 上**（逐例明细可由脚本重跑得到）：

| case | A 覆盖 | B 覆盖 | 增量 | 该 run 结果 |
|---|---|---|---|---|
| `13_tax_preparation` | 4/11 | **11/11** | +7 | ❌ |
| `15_college_enrollment` | 13/24 | **23/24** | +10 | ❌ |
| `19_wedding_venue` | 9/15 | **15/15** | +6 | ❌ |
| `17_veterinary_care` | 2/6 | **6/6** | +4 | ❌ |
| `20_daycare_enrollment` | 9/15 | 14/15 | +5 | ✅ |
| `18_retirement_planning` | 9/13 | 12/13 | +3 | ❌ |
| `16_home_renovation` | 7/10 | 9/10 | +2 | ❌ |
| `11_mortgage_application` | 1/4 | 3/4 | +2 | ❌ |
| `14_cellphone_upgrade` | 5/7 | 7/7 | +2 | ✅ |
| 其余 11 例 | 持平 | 持平 | 0 | — |

三条关键读数：

1. **现链在 15 行里丢掉了 36% 的判分数值**（47/132 不在窗口），而这 47 个 token 在库内是齐的
   （B 达到 95%，接近神谕上限）。**覆盖漏是机制问题，加窗可直接关掉。**
2. **成本可忽略**：注入字符 ×2.70，输入 token +76%（+413/例），而答案侧单例时延在 20s 量级、
   检索侧 `limit` 变化对 Milvus 查询时间影响 ~0。→ 用户的成本判断成立。
3. **C 相对 B 只多 1 个判分 token = case 16 的 `1800`**，代价是 18 条干扰句。
   即：**1 号的代价可离线量化（1 个 token），收益不可离线量化**（干扰句诱导错答属于答案层）。
   所以 1 号 的去留**必须端到端判**（§七），不能靠本表。

> 注：脚本对 A 的文本行做同一正则扫描会得到 3 处命中，经逐条核对**全是结构化事实**
> （case 14 `key=trade_in_penalty`、case 20 `key=vacation_week_tuition` / `vacation_tuition`），
> 不是 verbatim 噪声——这也正是 §5.1 说的"比较型中间值以结构化形态进窗"。

## 七、验收口径（方案确认后执行）

1. **三方对照**（同一份缓存库、judge=assert、struct provider）：
   A 现链 `top_k=15` / B 全入+1 号 / C 全入无 1 号。
   改检索/注入侧无需清缓存（AGENTS.md §4.3）→ 每轮 ≈12min。
2. **指标必须同时看**：覆盖漏（应大幅下降）、**回答漏**（唯一风险项，k=30 已有前车之鉴）、通过率。
3. **判读纪律**：同配置单轮可在 10~14/20 之间离散（实验记录 §4.1）→ 判定收益需同配置 ×3 轮取均值，
   或直接上 layer2。
4. **本方案的离线对照只给机制上限**（覆盖 64%→95%），不给通过率结论。

## 八、待决与风险

1. **1 号 的收益离线不可测**（§六-3）→ 需要 C 组端到端对照；若 C 组与 B 组无差异，1 号 可整体删除。
2. **layer2/3 预算**：46 行/case 是单会话速率，多会话线性累积（5 会话≈230 行≈1 万 tokens）。
   本机 layer2 数据为零（实验记录 §6.2），**无法验证**→ 故 §三-5 的 token 预算护栏必须保留，
   不能做成"无条件全入"。
3. **"精确检索"的口径未定**（上一轮讨论）：现行 `vec_storage.search` 只返回 dense+sparse **融合后**
   的单一列表，没有独立的"精确"通路；且 BM25 路对中文基本无召回（analyzer 不切词）。
   本方案**不依赖**它——但若要按"语义全入 + 精确全入"落地，需先定义它指哪一条
   （sparse/BM25 路 / 数值·实体倒排（新建） / verbatim 兜底集合）。
4. **唯一性不变量的破口**：跨机导入 `import_memory_batch` 不带 `entity_ref/attribute/lifecycle`
   （实验记录 §6.5 / 需求 13.9-8）→ 导入后投影键退化，2 号 若被删除则失去兜底。
   建议删 2 号 时把它转为**不变量断言 + 计数日志**（有重复才去重并打日志），而非静默删除逻辑。
5. **case 16 的 `$1,800`**：若选择保留 `instead of` 分支，必须同时落 §5.2 的收窄改法并补单测。

## 九、被否方案

| 方案 | 否决理由 |
|---|---|
| 保持现链不动 | 3 个组件实测 no-op / 失去对象；覆盖漏 64% 的事实说明复杂度没换来指标 |
| 无条件全入（无预算、无闸门） | C 组带进 18 条形式干扰句；layer2/3 会长到万级 token，无护栏 |
| 只把 top_k 上调（15→30），保留全链 | k=30 已实测：覆盖漏 18→5 但回答漏上升；且链仍要做无对象的配额分配 |
| 直接删掉 1 号（"既然要宽窗就全给 LLM"） | 判分块点名的"must not confuse"干扰值会直接进上下文，而离线指标测不出该损失 |
| 检索侧 LLM 判噪 | 每 query 一次额外 LLM 调用，成本/延迟不可接受，判据不稳定（沿用旧方案否决理由） |
| 引入 LLM rerank 替代链 | 当前瓶颈是**覆盖**（64%）不是**排序**；加窗已把覆盖推到 95%，rerank 的收益面被吃掉，却新增每 query 一次调用 |
| 立刻把 `k` 设为"全库无限" | layer2/3 无本地数据，风险不可测；应先有 token 预算护栏 |

## 十、附录：业界机制对照（学习笔记）

- **RAG 检索后处理**：主流做法是 rerank（cross-encoder/LLM）+ 去重 + 多样性（MMR），
  前提是**候选远多于预算**。本项目的特殊性在于：库本身很小（单 case ≈46 行），
  候选没有远多于预算，所以"分配器"这一层在宽窗下退化为空转——这是本方案的经验前提，
  不适用于大库场景。
- **预算式 context packing**：长上下文模型普及后，工程上更常见的是"按 token 预算塞满相关片段"
  而不是"固定条数 top-k"。本项目的 `top_k` 语义应由条数改为 token 预算，正是这一取向。
- **上下文稀释 / lost-in-the-middle**：上下文越长，模型对中段信息的利用率越低，这是
  "加窗降覆盖漏、升回答漏"现象的一般解释，也是本方案要求把结构化事实放在前面、
  原文片段标注归类的依据。
- **混合检索融合**：dense+sparse 经 RRF 或"dense 主导 + sparse 补盲"融合属常见做法；
  本项目已验证两种模式端到端持平（15.03→15.04），故融合模式不是本方案的变量。
