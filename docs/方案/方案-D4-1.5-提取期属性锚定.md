# D4-1.5 方案：提取期属性锚定（跨会话 canonical attribute 词表注入）

> 状态：**已实施（待 A/B 结论）** — 2026-09-14
> 归属：D4 系列的「归位层 · 属性归一」环节（主方案 §0.2 第 ② 行，此前唯一未解决项）。
> 主方案 [`方案-D4-实体归属与as-of版本裁决.md`](方案-D4-实体归属与as-of版本裁决.md) §8.3-1 的实现；
> 实体维度见 [`方案-D4-2-实体解析器.md`](方案-D4-2-实体解析器.md)。
> 红线不变：**裁决逻辑必须是确定性系统代码，不依赖 LLM 思考能力**——本方案只给模型
> 「字符串上下文」，要不要复用、复用哪条由模型产出 key，系统的归一/裁决仍是确定性代码。

---

## 1. 问题：属性漂移，裁决层看不见该打架的两条事实

### 1.1 病灶（case12 实证，主方案 §8.2）

```
amount        current = $95,000   wife_reversal(09-26)     ← 真值，但在独立命名空间
wire_amount   current = $100,000  husband_changes(09-25)   ← 停在旧值（簇内 latest）
```

同一桩电汇，模型在会话 1/2 写 `wire_amount`，会话 3 退化成泛词 `amount`。
两个命名空间各自 latest-wins，**谁也没覆盖谁**——注入窗口里两个金额并存，answer 无法判断 current。

### 1.2 为什么既有手段治不了

| 手段 | 为什么不够 |
|---|---|
| `_CANONICAL_ALIASES` 静态别名表（D4-1 L2） | 别名表要穷举「漂移到哪个泛词」；模型每次可以换一个词，O(漂移组合) 且事后才知道 |
| D4-2 实体维度（`entity_ref`） | 解决的是**多主体并存**（三种药、三张卡）；`amount` vs `wire_amount` 是**同一主体同一属性**，实体列切不动 |
| 时间序 as-of 裁决 | 裁决层是纯逻辑，前提是两条事实**签名相同**；签名不同则永远看不到彼此（主方案 §0.3-②） |

**结论**：这是**归位层**（把自由文本映射到确定性坐标）的问题，只能在提取期解决——
让模型**看见**该 user 已有的属性名，从而复用而不是另起炉灶。

## 2. 术语

| 术语 | 含义 |
|---|---|
| canonical attribute | 归一后的规范属性名（`normalize_key` 输出），即签名三元组里的 `attribute` |
| 属性词表 / 锚定词表 | 该 user 历史记忆中已存在的 canonical attribute 集合（按 category 分组） |
| 上下文锚定 | 把确定性状态（词表）作为**只读上下文**喂给模型，换取输出一致性；与「让模型做推理/裁决」是两件事 |
| 受控词表（controlled vocabulary） | 业界说法：抽取任务的输出空间被一份可管理的候选集约束 |

---

## 3. 设计

### 3.1 一句话

> **提取该 user 的后续会话时，把「他已有哪些属性名」渲染进 system prompt，
> 要求同一实体同一属性必须复用清单里的 key。**

### 3.2 prompt 侧（`core/extract/callers/deepseek_caller.py`）

新增规则 6 + 一个占位段（模板恒定，指纹随模板变更）：

```
6. **跨会话属性复用**：若下方「已有属性清单」中已有与本次事实**同一实体、同一属性**的 key，
   必须沿用该 key，禁止为它发明近义新 key（清单里已有 `wire_amount`，就不要再写
   `amount` / `transfer_amount`）。清单里没有的、或语义并不相同的，再自拟精确 key；
   同一属性全程只用一个 key。

## 已有属性清单（该用户历史记忆里的属性名，供跨会话复用）
{attribute_hints_section}
```

`render_attribute_hints_section()`（纯函数，可单测）渲染形如：

```
finance: wire_amount, wire_date, wire_reference
health: medication
```

- 按 category 分组、组内字典序 → **渲染确定性**（同一词表不同顺序输入输出一致）；
- 空/无效 → 中性占位 `（暂无历史属性；自拟 key 后请保持稳定复用。）`——
  **无词表 = 无锚定约束**，行为退化为「key 自拟」。

### 3.3 读侧（`core/services/struc_mem_service.py`）

```python
read_attribute_vocabulary(user_id, *, max_items=None) -> list[tuple[str, str]]
```

| 决策点 | 取值 | 理由 |
|---|---|---|
| 读哪个库 | **SQLite `struct_memories`** | 权威源在 SQLite，Milvus 只是投影（双写纪律）；投影可能滞后/重建中 |
| 哪些行 | `lifecycle='current'` | 历史名带生命周期前缀，模型按 current 名复用即可由 L2 归一器把 `original_*` 归到 historical 独立签名；把历史名也塞进清单反而**诱导**模型给现值加历史前缀 |
| 排除项 | `verbatim_*` / `raw_conversation*` | 兜底/降级行的 key 自身就是内容载体，复用它只会让后续会话也退化 |
| 排序与上限 | `(category, attribute)` 字典序 + `EXTRACT_ATTRIBUTE_HINTS_MAX`（默认 60） | 渲染确定性 + 防 prompt 膨胀；截断稳定可复现 |
| 失败姿态 | **任何异常 → 空词表 + WARNING** | 锚定是增益项，**绝不**能让提取因它中断（空词表 = 旧行为） |

### 3.4 透传链（不改裁决、不动 schema）

```
StrucMemService.add_structured_memory
  └─ read_attribute_vocabulary(user_id)                     ← 只读权威库
       └─ FactExtractor.extract_structured_facts(attribute_hints=…)
            └─ caller.extract(…, attribute_hints=…)          ← 协议扩参（base_caller）
                 └─ DeepSeekExtractionCaller.outcome(…, attribute_hints=…)
                      └─ render_attribute_hints_section() → system prompt
```

- 词表是**本次调用级参数**，不是 caller 状态：`_core_for(hints)` 有词表时现绑一个恢复核心
  （`generate` 闭包住词表），避免长对话并行分段共享可变状态；
- 无词表 → 复用长期持有的核心，**旧路径逐字节等价**；
- 开关 `EXTRACT_ATTRIBUTE_HINTS`（默认 True）：关闭 → 传 `None`（不读库、不渲染清单）；
- 观测：提取账日志加 `锚定语表=N`；`config_snapshot` 增 `extract_attribute_hints`（跑分可回溯）。

### 3.5 与「多值属性命名引导」的关系（本次未做）

D4-2 v2 的 P3（key 内实例名剥离）只在 LLM 主动写 `<属性>_<实例名>` 时生效，**非确定**。
那是另一条线（**D4-1.5b**：prompt 引导多值属性按 `<属性>_<实例名>` 命名），本次先做锚定
（收益面更大、不依赖模型新行为）。两条线互补：锚定治「同一属性换名」，命名引导治「多实例表达」。

## 4. 被否方案

| 方案 | 否决理由 |
|---|---|
| 扩充 `_CANONICAL_ALIASES` 静态表 | 追不上临场漂移（§1.2）；别名表 O(漂移组合) 膨胀，永远滞后 |
| L3 离线聚类灌词表 | 方向对但**事后**：新漂移先发生一轮、离线跑完才归一；作为周期性补充保留，不做主力 |
| 把词表塞进 user message | 污染对话内容（模型会把清单当作用户说的话），且与「消息即原文」的存储口径冲突 |
| 让模型输出权威 attribute/entity | 违反红线（裁决不靠模型推理）；本方案只给它字符串上下文 |
| 全量词表不分 category | 清单变长后噪声上升、复用误判风险增加；分组同时给了模型 category 线索 |
| 读 Milvus 投影当词表源 | 投影是派生数据（可能滞后/重建中），拿派生数据约束权威写入 = 因果倒置 |

## 5. 验证方式

### 5.1 单测（零 LLM）

`tests/unit/test_extract_attribute_hints.py`（11 例）：渲染分组/排序/空占位、caller 把词表
渲染进 system prompt 且不污染 repair、FactExtractor 单段与分段并行两条路径都透传、
读侧只取 current / 排除兜底属性 / 上限截断 / 异常回落空词表。
全量 `tests/unit` 回归 282 例绿。

### 5.2 A/B（离线回放，零落库）

`scripts/ab_extract_prompt.py anchor` —— 用例集 = 上一轮 layer2 实测（`run_2bf4dafd1b`，5/20）
的**全部失败用例**；layer2 天然多会话，直接取真实跨会话形态：

```
历史 = conversations[0..n-2]（旧 prompt 提取，模拟真实落库历史）
  └─ 词表 = 历史 facts 归一后的 (category, attribute) 集合（两臂共用，公平）
目标 = conversations[n-1]： old = v1.5 无锚定   vs   new = v1.6 词表注入
```

指标：

| 指标 | 定义 | 期望方向 |
|---|---|---|
| 复用率 | 目标会话 facts 中，归一后 `(category, attribute)` **命中词表**的比例 | ↑（漂移被压住） |
| 新属性面 | 归一后不在词表里的 distinct 属性数 | ↓（不再另起炉灶） |
| 数字保真 cov | 原句精确 token 被产出事实覆盖的比例 | 不降（不得为对齐词表丢数字） |
| facts / 属性数 | 产出规模与收敛度 | facts 不塌、属性数不膨胀 |
| in/out tokens | prompt 增量成本 | 增量可接受（词表 ≤60 条） |

**诚实边界**：回放只测**提取侧**（不含检索注入与 answer 判分）；词表来自旧 prompt 对历史
会话的提取，不等价于线上权威库的全部状态（如 superseded 行的影响）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| prompt 引导引入新的 key 漂移 | A/B 同时看「复用率」与「新属性面」；开关可一键关（`EXTRACT_ATTRIBUTE_HINTS=False`） |
| 词表过长挤占 prompt / 成本上升 | 上限 60 条 + 观测 token 增量 |
| 模型强行把新概念塞进清单里的旧 key（过度复用） | 规则 6 明写「语义并不相同的，再自拟精确 key」；A/B 看 facts/属性数是否异常收缩 |
| 词表读失败影响提取 | 读侧全异常回落空词表（空 = 无锚定） |
| 并行分段竞争 | 词表按调用绑定（不写 caller 状态） |

## 7. 附录：业界机制对照（学习笔记）

- **受控词表 / 术语表注入（controlled vocabulary & glossary grounding）**：抽取类任务的常见做法是
  把「允许/推荐使用的字段名」作为上下文给出，降低自由生成带来的命名熵——本方案就是它在
  跨会话记忆场景的实例。
- **Schema-guided extraction**：LLM 结构化抽取（如 function calling 的 JSON schema）把输出空间的
  一部分交给系统约束。本项目没有强约束 key（那会违「宽进存储」铁律），而是**软引导**：
  清单是建议、裁决仍在系统侧。
- **上下文锚定 vs 模型推理**：区别在于「给状态」还是「要判断」。给状态（词表）是确定性的、
  可审计的；要判断（哪个是同一属性）等于把裁决推回模型——本项目红线禁止。
- **RDF 对照**：`attribute` 相当于 predicate，本方案做的事相当于让抽取器**复用本体里的谓词名**，
  而不是每次自由造谓词。
