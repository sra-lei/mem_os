## P0 — 阻塞 layer2 分数的核心缺口

### 1. D4：实体归属 & as-of 版本裁决方案（最大瓶颈）
- **现状**：layer2 15/20 挂，大半是"同一实体多版本并存"问题（如 12 电汇 $85k→$100k→$95k、日期 10/1→9/27→10/1；10 航班改签链；11 诊疗演进；20 医保变更）。注入端多个版本全在 → answer 拿不到"最新正确值"。
- **根因**：提取侧是纯增量（有什么加什么），没有"同实体新值覆盖旧值"的裁决逻辑；key 命名漂移又加剧了同事实多版本并存。
- **范围**：提取侧 → 入库前比对 → 同实体同属性 upsert / 历史归档；key 标准化降漂移。
- **依赖**：实体归一化规则定义（哪些 category 走版本裁决？person/finance/health/plan 肯定要，contact 可能要）。
- **产出**：方案文档 → 小批量验证（3-5 个矛盾用例）→ 全量复测。
- **风险**：裁决逻辑写死可能误伤（同名下不同实体 = 误合并）；需可审计（保留版本链）。

### 2. 建立稳定基线（消除 case 级噪声）
- **现状**：同配置同用例双峰震荡（09: 0.2↔0.8、13: 1.0→0.0、17: 0.2↔0.8、06: 0.29↔0.71）。单次跑分不可比，任何变更收益都难以统计显著。
- **行动**：同配置 × 3 轮 → 取均值/中位数 → 建立"稳定通过集"；脚本化批量跑 + 自动汇总。
- **成本估计**：10-15 分钟/轮 × 3 轮 = 30-45 分钟/全量基线。
- **产出**：基线脚本 + 一张稳定分数表（含方差）。

## P2 — 优化与基础设施

### 6. 跨用例并行（runner 层）
- **现状**：全量 20 例串行跑 20+ 分钟；瓶颈在 answer（每个几秒到几十秒）+ 提取（每个会话几秒）。SQLite 单写者 + Milvus 并发写未验证。
- **行动**：先验证 SQLite 并发读+写安全性（WAL 模式下读不阻塞写，写串行），再开 N 进程并行 answer。
- **收益**：全量评测从 23min → 5-8min。
- **风险**：SQLite 并发写冲突；Milvus 重复插入；需要加锁或用例级隔离。

### 7. answer 侧时间优化
- **现状**：answer 开思考每例几秒到几十秒（平均 ~1min）。占总时长 ~60%。
- **方向**：answer prompt 缩短；小模型 answer（如用 deepseek-v4-flash 不开思考做 answer 基线，对比质量）；缓存相同问题。
- **优先级低**：23 分钟全量已可接受。

### 8. 提取并发精细化（对话内）
- **现状**：ThreadPoolExecutor(min(4, chunks)) 已存在。层2 会话 2-3 块、收益有限。
- **方向**：worker 数参数化上限取 profile.max_concurrency；结果按 chunk 序号归并；executor 注入。
- **价值**：架构整洁 > 性能收益。

### 9. Milvus schema value 上限 1024 的长期方案
- **现状**：降级切片 ≤900 字符已修复崩溃，但 1024 上限本身是隐患（未来可能有更长的 verbatim 兜底）。
- **方向**：schema 升级 value VARCHAR(4096) 或 TEXT；或长文本存 SQLite 仅 key 进 Milvus。
- **优先级低**：当前防线够用。

1. **deepseek-v4-flash 默认思考模式 ON**——reasoning_content 吃 8192 预算 → content 空截断 + 数倍延迟。简单结构化任务（提取）永远关思考；合成/消歧类（answer）开思考。
