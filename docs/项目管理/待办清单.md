### 0.1 一句话

> **记忆不是"有什么加什么"，而是"同一个人/物的同一个属性，永远只有一条当前值"。**

D4 做的是给每条事实加**三维定位**，让"同一属性"的事实能互相认出来，
从而做到**新值覆盖旧值**（版本裁决）而不是无限堆叠。

### 0.2 四个概念（理解 D4 的全部）

| 概念 | 回答的问题 | 取值 | 例子 |
|---|---|---|---|
| `entity_ref` | **是谁**的 | `SELF`（本人）/ `ID:VEL` / `PROD:MAT-151` / `DRUG:甲氨蝶呤` | 防覆盖机制 |
| `attribute` | 是**什么性质**的 | 规范属性名 | `wire_amount`、`medication` |
| `lifecycle` | **时序**位置 | `current` / `historical` | 当前值 / 历史快照 |
| **签名** | — | 上面三者的组合 | `(SELF, wire_amount, current)` |

**裁决规则**：同签名 → 新版本**覆盖**旧版本（旧值转 `historical` 保留版本链）。

**关键反直觉点**：`entity_ref` 首先是一道**防覆盖**机制，不只是"支持多人多账户"。
归一做得越好，误并风险越大——所以宁可裂开（冗余），不可丢失。

### 0.3 一半事实是"单值"，一半是"多值"

这是 D4-2 v2 补上的关键区分：

| 属性类型 | 语义 | 多个值意味着 | 处理 |
|---|---|---|---|
| **functional**（单值，缺省） | 一个属性只有一个当前值 | **版本演进**（$85k→$100k→$95k） | 保持同签名 → 走版本裁决 |
| **multi_valued**（多值） | 值的集合本身有意义 | **多个实例并存**（三种药、三张卡） | 值升级为实例 → 进 `entity_ref` |

> **单值属性绝不按值切分**——这是安全阀。切了就会把版本链打碎。
> 白名单**只收实证确认的**，首批 7 项（health/medication、education/course×3、finance/信用卡与账户×3）。

## P0 — 阻塞主指标的缺口

### 1. 【新，2026-09-12】检索/注入侧瓶颈

- **现状**：D4-2 v2 三用例复测**答案层零变化**，但查证发现**必要事实全在库里，只是没被注入**：
  - **11 房贷**：Chase `$18,500` / Wells Fargo `$67,000` / Marcus `$45,000` 三条**全在库**，
    但注入窗口给的是投资/退休账户 → 答案 LLM 明确回"档案中没有记录这两个账户的具体余额"；
  - **15 选课**：四门课 + 教授 + 时段**全在库**，但注入的 15 条里 **14 条是财务类**（学费/住宿/餐费）。
- **根因**：`top_k` 是**钝器**——语义相关的**后段名次分差**（0.003–0.030）**小于噪声地板**（0.017），
  即从第 3 名往后"更相关"其实是噪音；而这正是 embedding 打**话题分**而非**答案分**的必然结果
  （抹掉数字对相似度的影响只有 |Δsim|=0.017，约 2%）。
- **方向**（按性价比排序）：
  1. **答案级信号**补进排序：BM25 命中 / 值匹配（问 $130,500 → 让含该数字的条目前置）；
  2. **出路 A：换渲染**——`struct_provider` 现在是扁平散文列表，改成按 category 分组/表格，
     让同样 15 条承载更多信息（降低"稀释"）；
  3. top_k 继续加大：天花板 ≈18/20，但后段加分是随机的，**优先度最低**。
- **验证**：三个用例（03/11/15）+ 全量 layer1 对比。
- **依赖**：无（可立即开工）。

### 2. 建立稳定基线（消除 case 级噪声）

- **现状**：同配置同用例双峰震荡（09: 0.2↔0.8、13: 1.0→0.0、17: 0.2↔0.8、06: 0.29↔0.71）。
  单次跑分不可比，任何变更收益都难以统计显著。20 例分辨率下，单臂单轮差 ≤2 例**判不了**。
- **行动**：同配置 × 3 轮 → 取均值/中位数 → 建立"稳定通过集"；脚本化批量跑 + 自动汇总。
- **成本**：10-15 分钟/轮 × 3 轮 = 30-45 分钟/全量基线。
- **产出**：基线脚本 + 一张稳定分数表（含方差）。

## P2 — 优化与基础设施

### 7. 跨用例并行（runner 层）

- **现状**：全量 20 例串行跑 20+ 分钟；瓶颈在 answer（几秒到几十秒/例）+ 提取（几秒/会话）。
  SQLite 单写者 + Milvus 并发写未验证。
- **行动**：先验证 SQLite 并发读+写安全性（WAL 模式下读不阻塞写，写串行），再开 N 进程并行 answer。
- **收益**：全量评测 23min → 5-8min。**风险**：SQLite 并发写冲突；Milvus 重复插入。

### 8. answer 侧时间优化

- **现状**：answer 开思考每例平均 ~1min，占总时长 ~60%。
- **方向**：answer prompt 缩短；小模型 answer（用 `deepseek-v4-flash` 不开思考做基线对比质量）；缓存相同问题。
- **优先级低**：23 分钟全量已可接受。

### 9. 提取并发精细化（对话内）

- **现状**：`ThreadPoolExecutor(min(4, chunks))` 已存在。层2 会话 2-3 块、收益有限。
- **方向**：worker 数参数化上限取 `profile.max_concurrency`；结果按 chunk 序号归并；executor 注入。
- **价值**：架构整洁 > 性能收益。

### 10. Milvus schema value 上限 1024 的长期方案

- **现状**：降级切片 ≤900 字符已修复崩溃，但 1024 上限本身是隐患（未来可能有更长的 verbatim 兜底）。
- **方向**：schema 升级 `value VARCHAR(4096)` 或 `TEXT`；或长文本存 SQLite 只 key 进 Milvus。
- **优先级低**：当前防线够用。

## 方法学教训（经验沉淀）

1. **deepseek-v4-flash 默认思考模式 ON**——`reasoning_content` 吃 8192 预算 → content 空截断 +
   数倍延迟。简单结构化任务（提取）永远关思考；合成/消歧类（answer）开思考。
2. **case 级单次跑分不可比**——layer2 top-20 注入有随机性（key 命名漂移 → 排序变 → top-20 内容变）。
   严判需同配置 × 2-3 轮取均值。
3. **prompt 文本不是主杠杆**——v1/v1.5/旧 在"关思考"条件下端到端差异在噪声带内（5-6/20）。
   真正杠杆是思考模式开关 + 架构（D4）。
4. **AB 实验零落库纪律**——不写 memories.db / Milvus / conv_meta，纯内存回放，可重复、可对比、零副作用。
5. **【09-12】审计归零 ≠ 零缺失**——审计脚本靠"兜底句被剪但 token 在落库事实里找不到"来判定，
   只覆盖**有兜底句可对照**的那一半。没数字的事实（`User's dog is named Max`）没有兜底句 → 真丢了也测不出。
6. **【09-12】"丢弃"要分两类**——批内同签名收敛丢弃的样本里，**有相当比例是"同一事实换个说法"的合法去重**
   （11 房贷的三个样本都是）。**真丢失的特征是：被丢弃事实在库中找不到语义等价行。**
   不做这一步对照，会把去重误判成事故、把修法做偏。
7. **【09-12】改提取行为，先写方案文档再动手**——D4-2 v2 的价值不在"设计多巧妙"，而在
   **跑一遍就暴露了设计者想不到的错**（复合属性名被误当实例名：`DRUG:supply` / `CARD:balance`）。
   **小步实测 + 确定性护栏**，比一次想全更省。
8. **【09-12】先分清楚"失败在哪一层"再优化**——D4-2 v2 三用例答案层零变化，深挖发现
   失败点根本不在实体层（事实全在库，是检索没注入）。**不做这层定位，会在错误的层反复投入。**
