# MemOS 需求文档

## 文档说明

- **项目名称**：MemOS（Memory Operating System）
- **文档版本**：v1.0
- **目标读者**：开发者（用于指导工程实现）
- **文档结构**：按版本演进组织，每个版本包含完整的模块定义、验收标准和迭代目标

---

## 总览

### MemOS 是什么

MemOS 是一个从零构建的 Agent 用户记忆系统，用于**跨会话记住用户信息并提供个性化服务**。它不依赖任何现成的记忆框架，完全基于第三章的理论体系实现，通过四个版本的渐进式演进，最终成为一个包含写入、存储、检索、压缩、遗忘、审核等完整模块的生产级记忆系统。

### 设计原则

1. **先跑通，再优化**：每个版本只引入必要的复杂度
2. **验证集驱动**：每个版本都有明确的通过率目标
3. **可观测性优先**：从第一天起就记录所有操作日志
4. **工程决策有据**：每次迭代记录选择了什么、放弃了什么、为什么

### 版本路线图

| 版本 | 主题 | 通过率目标 | 核心新增 |
|------|------|-----------|----------|
| v0.1 | 基础记忆系统 | ≥90%（基础回忆） | Simple Notes + BM25 + 日志脱敏 |
| v0.2 | 结构化与向量检索 | ≥80%（新增多会话检索） | JSON Cards + 向量检索 + 冲突检测 |
| v0.3 | 高级检索与压缩 | ≥75%（新增主动服务） | Advanced JSON Cards + 混合检索 + 压缩机制 |
| v0.4 | 系统化与自主化 | ≥85%（全量回归） | 审核机制 + 智能体RAG + 程序记忆 |

# v0.1：基础记忆系统

## 版本目标

构建一个能"记住"和"回忆"的极简系统，验证端到端流程的可行性。不追求任何形式的优化或智能化，只做最基础的读写。

**通过率目标**：≥90%（在20个基础回忆用例上）

## 模块设计

### 模块 1.1：日志脱敏（基础安全设施）

**职责**：所有写入和检索操作的日志在落盘前必须脱敏

**实现方案**：

- 基于正则表达式的 PII 快速检测（身份证、手机号、邮箱、银行卡）
- 敏感字段在日志中以 `[REDACTED]` 替代
- 脱敏后的日志仍保留结构化信息（如"提取到 1 条事实"）

**为什么在 v0.1 就要做**：日志脱敏决定了你是否能安全地查看调试信息。第一阶段不做，后面所有阶段的调试都会被隐私风险阻碍。

**工程决策**：
- 选择方案：本地正则表达式（不调用LLM）
- 理由：成本几乎为零，足够覆盖80%的PII场景
- 备选方案：本地小模型检测，留待v0.3引入

### 模块 1.2：数据模型（Simple Notes）

**职责**：定义记忆的存储格式

**数据结构**：

```python
@dataclass
class Memory:
    id: str                    # UUID
    user_id: str               # 用户唯一标识
    fact: str                  # 纯文本事实，如"用户邮箱是john@example.com"
    source_session_id: str     # 来源会话ID
    created_at: datetime       # 创建时间
    # v0.1 不做任何结构化，只存纯文本
```

**存储**：SQLite 一张表 `memories`，每行一条记忆。

**工程决策**：
- 选择方案：SQLite + 纯文本
- 理由：零额外依赖，便于调试，足够支持v0.1
- 备选方案：PostgreSQL，待v0.2引入

### 模块 1.3：写入流程

**职责**：会话结束后，从对话历史中提取事实并写入存储

**触发条件**：每次会话结束后（由上层 Agent 框架调用）

**实现步骤**：

1. 获取最近一次会话的完整轨迹（用户消息 + Agent 回复）
2. 调用提取 LLM（使用轻量模型，如 Qwen2.5-0.5B）
   - System Prompt：*从对话中提取出值得长期记住的事实，每条事实独立成句，不超过3条。只提取对未来有用的稳定信息，不提取临时性细节。*
   - 输出：JSON 数组 `["fact1", "fact2", ...]`
3. 对每条事实，构造 Memory 对象并写入 SQLite
4. 写入日志经脱敏后记录

**异常处理**：
- LLM 提取失败 → 记录错误但不阻塞（静默跳过本次会话）
- 写入失败 → 重试3次，仍失败则记录错误

**工程决策**：
- 选择方案：每次会话结束后同步调用LLM提取
- 理由：v0.1 以简单优先，不引入异步队列
- 代价：写操作会阻塞会话结束响应（但当前场景下可接受）

### 模块 1.4：检索流程

**职责**：根据用户当前输入，召回最相关的 K 条记忆

**实现步骤**：

1. 接收用户当前输入 `query`
2. 对 `query` 进行简单分词（按空格和标点切分）
3. 从 SQLite 中查询所有该用户的记忆
4. 使用 BM25 算法对每条记忆的 `fact` 字段计算与 `query` 的匹配度
5. 按 BM25 得分降序排列，取 Top-K（K=3）
6. 返回记忆列表

**BM25 参数**（固定值）：
- `k1 = 1.5`
- `b = 0.75`

**工程决策**：
- 选择方案：全量扫描 + BM25 实时计算
- 理由：v0.1 记忆数量有限（单用户 < 100 条），全量扫描无需索引
- 代价：随记忆增长会变慢，计划在 v0.2 解决

### 模块 1.5：注入流程

**职责**：将检索到的记忆注入到 Agent 的系统提示词中

**实现方式**：

在每次 Agent 调用前，将检索到的记忆拼接到 System Prompt 的末尾：

```
## 关于用户的长久记忆
以下是该用户之前说过的一些信息，供你参考：
- {memory_1.fact}
- {memory_2.fact}
- {memory_3.fact}
```

**工程决策**：
- 选择方案：直接拼接纯文本
- 理由：简单有效，v0.1不涉及格式化或结构化处理
- 备选方案：结构化注入（如 JSON），待 v0.2 引入

## v0.1 验证集

**构建方式**：人工构造20个基础回忆测试用例

**用例结构**：
- **建立阶段**：一段用户与 Agent 的对话（包含要记住的信息）
- **查询阶段**：一个用户问题（应直接触发对已记住信息的回忆）
- **期望答案**：回答应包含的精确信息

**用例示例**：

```
用例ID: R-001
名称: 记住用户邮箱
建立对话:
  User: "我是 John，我的邮箱是 john.doe@gmail.com"
  Agent: "好的，我已记下你的邮箱"
查询问题: "我的邮箱是多少？"
期望答案: 应包含 "john.doe@gmail.com"
```

**通过标准**：LLM-as-Judge 判定 Agent 的回答包含了期望答案的核心信息。

## v0.1 验收标准

| 验收项 | 标准 |
|--------|------|
| 功能完整性 | 写入 → 存储 → 检索 → 注入 全流程可运行 |
| 验证集通过率 | ≥90%（18/20） |
| 日志脱敏 | 所有日志中无明文 PII |
| 错误处理 | LLM 提取失败时不阻塞，写入失败时重试 |

## v0.1 工程决策总结

| 决策点 | 选择 | 理由 | 备选方案 |
|--------|------|------|----------|
| 存储介质 | SQLite | 零依赖，便于调试 | PostgreSQL（v0.2） |
| 数据格式 | 纯文本 | 最简单 | 结构化（v0.2） |
| 检索算法 | BM25 全量扫描 | 小数据量下足够 | 倒排索引（v0.3） |
| 提取模型 | Qwen2.5-0.5B | 轻量、本地可跑 | 更强模型（v0.3） |
| 脱敏方式 | 正则表达式 | 成本为零 | LLM检测（v0.3） |
| 写入方式 | 同步阻塞 | 简单 | 异步队列（v0.3） |

# v0.2：结构化与向量检索

## 版本目标

解决 v0.1 的两个核心短板：
1. 纯文本无法按主题查询（如"我所有的旅行记录"）
2. BM25 无法处理语义相似查询（如"kitty"匹配不到"cat"）

**通过率目标**：≥80%（在新增的20个多会话检索用例上），原有基础回忆用例通过率不降。

## 模块变更

### 变更 2.1：数据模型升级

**从 Simple Notes 升级到 JSON Cards**

```python
# v0.2 的 Memory 结构
@dataclass
class Memory:
    id: str
    user_id: str
    category: str              # 主题：personal / travel / work / health / ...
    subcategory: Optional[str]  # 子主题：contact / preference / history / ...
    key: str                   # 字段名：email / seat_preference / ...
    value: str                 # 字段值：john@example.com / window / ...
    source_session_id: str
    created_at: datetime
    updated_at: datetime       # 新增：记录最后更新时间
```

**分类规则**（写入时由 LLM 自动分类）：
- `personal.contact`：姓名、邮箱、电话
- `personal.preference`：饮食偏好、座位偏好
- `travel.history`：过往旅行记录
- `work.position`：职位、公司
- `health.allergy`：过敏信息

**工程决策**：
- 选择方案：在提取阶段由 LLM 同时输出 fact + category + subcategory + key
- 理由：一次调用完成分类，不增加额外LLM调用
- 代价：Prompt 更复杂，可能降低提取准确率

### 变更 2.2：存储层升级

**从 SQLite 迁移到 PostgreSQL + pgvector**

**迁移策略**：
1. 保留 v0.1 的 SQLite 数据用于回滚
2. 编写迁移脚本，将 v0.1 数据导入 PostgreSQL
3. 所有新写入同时写入 PostgreSQL

**为什么不是可选项**：pgvector 是 v0.2 向量检索的必要依赖。

**工程决策**：
- 选择方案：PostgreSQL + pgvector 扩展
- 理由：单一数据库同时支持结构化查询和向量检索，降低运维复杂度
- 备选方案：SQLite + 独立向量库（如 Chroma），复杂度更高

### 变更 2.3：写入流程增强

**增加：冲突检测机制**

当写入一条新记忆时，检查同一 `(user_id, category, subcategory, key)` 是否已有记录：
- 如有 → 执行 **UPDATE**（新值覆盖旧值），旧值存入 `previous_values` 历史记录
- 如无 → 执行 **INSERT**

**历史记录存储**（新增字段）：
```python
previous_values: List[Dict]  # [{"value": "北京", "at": "2026-08-01"}, ...]
```

**工程决策**：
- 选择方案：按同一 key 覆盖（非追加）
- 理由：结构化数据追求"当前准确值"，历史保留在单独字段而非污染主表
- 代价：丢失了"用户曾说过什么"的完整时间线（将在 v0.3 用时间加权检索补偿）

### 变更 2.4：检索流程升级

**增加：向量检索**

1. 使用嵌入模型（如 BGE-M3 或 text-embedding-3-small）将 `query` 转为向量
2. 使用 pgvector 的余弦相似度检索，召回 Top-5
3. 与 BM25 结果合并（v0.2 采用简单合并：取两路结果中得分最高的 3 条）

**检索策略**：
```
1. BM25 检索 → Top-3
2. 向量检索 → Top-3
3. 合并去重 → 按得分排序取 Top-3
```

**工程决策**：
- 选择方案：BM25 + 向量检索 简单合并
- 理由：先验证向量检索的价值，再考虑复杂融合
- 备选方案：RRF 融合（留待 v0.3）

## v0.2 验证集

**新增：20个多会话检索用例**

**用例特征**：
- 信息分布在 2-3 个不同的会话中
- 需要跨会话关联才能回答
- 可能涉及同一实体的多个实例（如"两辆车"）

**用例示例**：

```
用例ID: M-001
名称: 多辆车预约保养
建立对话-会话1:
  User: "我的本田 Accord 需要预约保养"
  Agent: "好的，我会记录你的本田需要保养"
建立对话-会话2（不同时间）:
  User: "我刚买了辆特斯拉 Model 3"
  Agent: "收到，已记录你的特斯拉"
查询问题: "我需要为我的车预约服务"
期望答案: 应提到两辆车（本田 Accord 和特斯拉 Model 3），并询问具体哪辆
```

## v0.2 验收标准

| 验收项 | 标准 |
|--------|------|
| 数据迁移 | v0.1 数据完整迁移至 PostgreSQL |
| 结构化写入 | 每条记忆自动分类，冲突检测生效 |
| 向量检索 | 能召回语义相关但无关键词匹配的记忆 |
| 多会话用例通过率 | ≥80%（16/20） |
| 基础回忆用例通过率 | 不低于 v0.1 的 90% |

## v0.2 工程决策总结

| 决策点 | 选择 | 理由 | 备选方案 |
|--------|------|------|----------|
| 存储 | PostgreSQL + pgvector | 统一存储，支持混合查询 | SQLite + Chroma |
| 冲突处理 | 按 key 覆盖 + 历史归档 | 结构化数据取当前值 | 仅追加（v0.3讨论） |
| 检索融合 | 两路简单合并取Top3 | 先验证向量检索效果 | RRF融合（v0.3） |
| 嵌入模型 | BGE-M3（本地） | 开源、可离线 | OpenAI Embedding（v0.3可选） |

# v0.3：高级检索与压缩

## 版本目标

解决 v0.2 的三个短板：
1. JSON Cards 的刚性分类无法处理多维属性（如"周末用 Python 开发个人项目"）
2. 简单合并检索无法处理同义表达和深度相关性
3. 记忆只增不减，长期运行后检索精度下降

**通过率目标**：≥75%（在新增的20个主动服务用例上），原有用例通过率不降。

## 模块变更

### 变更 3.1：数据模型升级

**从 JSON Cards 升级到 Advanced JSON Cards**

```python
@dataclass
class Memory:
    # 基础字段
    id: str
    user_id: str
    
    # 核心事实
    fact: str                  # 完整自然语言描述
    category: str
    subcategory: Optional[str]
    key: str
    value: str
    
    # Advanced JSON Cards 新增字段
    backstory: Optional[str]   # 信息来源的上下文："用户在讨论去东京的航班时提到"
    person: Optional[str]      # 主体："用户本人" / "父亲张伟" / "女儿李芳"
    relationship: Optional[str] # 与用户的关系："本人" / "父亲" / "女儿"
    timestamp: datetime        # 事实对应的具体时间（非存储时间）
    confidence: float          # 置信度 0-1
    source_evidence: str       # 原始证据标识（会话ID或文档引用）
    
    # 原有字段
    source_session_id: str
    created_at: datetime
    updated_at: datetime
    previous_values: List[Dict]
```

**person 字段的消歧作用**：
- 同一个用户说"张医生是我的牙科医生" → `person="用户本人", relationship="本人"`
- 用户说"我父亲的心脏科医生也是张医生" → `person="父亲", relationship="父亲"`
- 检索"张医生"时可以关联 `relationship` 字段区分

**工程决策**：
- 选择方案：所有新写入都要求 LLM 输出 backstory/person/relationship
- 理由：这些字段是实体消歧和主动服务的基础
- 代价：写入的 LLM 调用成本增加约 50%（Prompt 更长，输出更复杂）

### 变更 3.2：写入流程升级

**增加：异步队列 + 强模型提取**

**新流程**：
1. 会话结束后，写入任务放入异步队列（不阻塞会话响应）
2. 后台 Worker 消费队列，调用更强模型（如 GPT-4o-mini 或 Qwen2.5-7B）
3. 模型输出包含：fact, category, subcategory, key, value, backstory, person, relationship, timestamp
4. 执行冲突检测和历史归档
5. 写入 PostgreSQL

**为什么需要异步**：v0.3 的写入成本是 v0.2 的 5-10 倍（更强模型 + 更多输出字段），同步阻塞不可接受。

**工程决策**：
- 选择方案：Redis Queue 或 Celery
- 理由：简单可靠，适合单机部署
- 备选方案：Kafka（分布式场景）

### 变更 3.3：记忆压缩与整理机制

**首次引入**：定期（每周）压缩整理

**三层压缩**：

**第一层：重要性评分**
```python
def importance_score(memory: Memory) -> float:
    score = 0.0
    score += 0.3 * access_count(memory.id)      # 访问频率
    score += 0.2 * time_decay(memory.created_at) # 时间衰减（越近越高）
    score += 0.2 * memory.confidence             # 置信度
    score += 0.2 * uniqueness_score(memory)      # 信息独特性（与其他记忆的差异度）
    score += 0.1 * (1 if memory.relationship == "本人" else 0) # 本人信息优先
    return score
```

- 低于阈值（如 0.3）的记忆标记为"待压缩"

**第二层：聚类与摘要**
- 对同一 `(user_id, category)` 的记忆进行语义聚类
- 每组生成一条摘要："用户经常询问天气，特别关心降雨"
- 原始记忆归档到二级存储（仍可追溯）

**第三层：抽象与泛化**
- 从多次同类行为中提取模式，转化为程序记忆
- 示例：3次订机票流程 → 提炼为"用户订机票时依次需要：搜索→确认座位→使用常旅客号→订餐"
- 程序记忆单独存储（见 v0.4 模块）

**工程决策**：
- 选择方案：每周六凌晨执行全量压缩
- 理由：定期执行比实时执行更可控
- 代价：首次压缩可能需要数小时（视数据量而定）

### 变更 3.4：检索流程升级

**升级为混合检索流水线**

```
阶段1：并行检索
  ├── BM25 检索 → Top-20
  └── 向量检索 → Top-20

阶段2：结果融合（RRF）
  └── 融合得分 = Σ 1/(60 + rank)

阶段3：神经重排序
  └── Cross-Encoder（如 bge-reranker-v2-m3）对融合后的 Top-10 逐对评分
  └── 输出最终排序的 Top-3
```

**引入时间加权**：
- 检索时，对召回结果额外增加时间权重：`最终得分 = 原始得分 * (1 + 0.2 * time_weight)`
- 时间权重：7天内的事实 +50%，30天内 +20%，30天以上不加权

**工程决策**：
- 选择方案：完整三阶段流水线
- 理由：这是生产级 RAG 的标准配置，值得完整实现和学习
- 代价：检索延迟从 <100ms 增加到 500-1000ms

## v0.3 验证集

**新增：20个主动服务用例**

**用例特征**：
- 用户没有明确提出，但系统应主动发现并提供帮助
- 需要综合多个会话的信息进行推理
- 可能涉及时间推理（如"护照即将过期"）

**用例示例**：

```
用例ID: A-001

期望行为: Agent 发现护照日期（2月18日）与旅行日期（1月15日）接近，主动提醒 "你的护照将在旅行后一个月过期，建议检查目的地入境要求"
```

# v0.4：系统化与自主化

## 版本目标

解决 v0.3 的三个短板：
1. 知识无法自主更新——旧知识会过时，但系统不会主动修正
2. 检索仍然是"一次性查询"——Agent 无法多轮迭代探索
3. 程序记忆未系统化——积累了流程模式但未形成可复用能力

**通过率目标**：≥85%（全量60个用例回归测试）

## 模块变更

### 变更 4.1：数据模型 - 混合模型

**核心理念**：记忆分成两个层次

| 层次 | 内容 | 存储位置 | 更新方式 |
|------|------|----------|----------|
| **常驻概览** | Advanced JSON Cards 中的核心事实（高置信度、高访问频率） | 直接在 Agent 上下文中注入 | 写入时同步更新 |
| **按需细节** | 原始对话的完整轨迹，通过上下文感知检索按需召回 | RAG 知识库（向量检索） | 写入时追加，不修改 |

**上下文感知检索在前缀中的应用**：
- 对话轨迹在写入向量库之前，先用 LLM 生成上下文前缀
- 示例：原本孤立的块"好的，就订这个吧" → 加前缀"[用户正在预订从上海到西雅图的单程机票，价格500美元]"

**工程决策**：
- 选择方案：双层存储（SQLite 存概览 + 向量库存细节）
- 理由：兼顾"随时可见"和"按需深入"
- 代价：需要维护两套存储的一致性

### 变更 4.2：增量更新 - Proposer-Reviewer 审核机制

**核心理念**：知识更新不能由单个模型独自决定，需要经过"提议→审核→合入"流程

**流程**：

```
1. Proposer Agent 提交 PR
   - 从新会话中提取事实
   - 检索相关已有知识
   - 在工作分支上提交 diff（增/删/改）
   - 附上证据引用（原始会话ID）

2. Reviewer Agent 独立审核
   - 拿到变更前的知识 + diff + 原始证据
   - 检查：
     a. 每个新断言是否有证据支持
     b. 是否遗漏限定条件
     c. 是否与其他文件冲突
     d. 删除/改写是否过度
   - 返回：批准 / 拒绝 + 理由

3. 双方迭代至收敛
   - 最大迭代 3 次
   - 超时转人工审核（记录待处理）

4. 合入主库
   - CI 检查：格式、链接、元数据
   - 增量重建受影响的分块和索引
```

**工程决策**：
- 选择方案：Proposer 和 Reviewer 使用不同家族的模型
  - Proposer：Claude Sonnet（擅长分析）
  - Reviewer：GPT-4o（擅长批判性检查）
- 理由：异源模型可降低同类错误
- 代价：成本翻倍，延迟增加

### 变更 4.3：定期整理 - 全量去重与合并

**触发条件**（任一满足）：
- 距离上次整理 > 30 天
- 记忆总数 > 5000 条
- 检索失败率连续 7 天 > 15%

**执行内容**：
1. **去重**：识别语义相似 > 90% 的记忆，合并为一条
2. **去旧**：标记时间超过 1 年且访问次数 < 3 的记忆为"归档"
3. **冲突解决**：遇到矛盾信息时，追溯各自证据源，标注适用场景（而非强行删除）
4. **索引重建**：全量重建向量索引（解决长期增量插入后的精度下降）

**工程决策**：
- 选择方案：定时任务 + 人工审核关键冲突
- 理由：全量整理涉及数据删除，必须有监督
- 代价：大型知识库整理可能需要数小时

### 变更 4.4：程序记忆系统化

**核心理念**：从多次交互中提炼可复用的行为模式

**程序记忆的存储**：

```python
@dataclass
class ProceduralMemory:
    id: str
    user_id: str
    name: str                  # "订机票流程"
    description: str           # 自然语言描述
    steps: List[str]           # ["搜索直飞航班", "确认座位偏好", "使用常旅客号", "订餐"]
    source_memories: List[str]  # 来源的情景记忆 ID
    confidence: float          # 置信度（基于验证次数）
    created_at: datetime
    last_used_at: datetime
```

**提炼时机**：
- 每次会话结束后，检查是否有 3 次以上的相似行为
- 如有 → 提炼为程序记忆
- 程序记忆以 JSON Cards 格式存储，单独分类 `procedural.*`

**工程决策**：
- 选择方案：由单独的 LLM 任务定期扫描情景记忆，发现模式
- 理由：实时发现模式成本太高，定期扫描更可控
- 代价：需额外的模式识别逻辑

### 变更 4.5：检索升级 - 智能体化 RAG

**核心理念**：检索是 Agent 的自主迭代探索，而非一次性查询

**实现方式**：

Agent 拥有工具 `search_user_memory(query: str) -> List[Memory]`

ReAct 循环：
```
1. 思考：分析用户问题，确定需要什么信息
2. 行动：调用 search_user_memory，使用具体关键词
3. 观察：评估召回结果是否充分
4. 如果不充分 → 回到步骤1，使用更精确或不同角度的查询
5. 如果充分 → 综合所有信息生成回答
```

**示例流程**：
```
用户："我上次说的那个项目预算后来批了吗？"

思考：需要先确定"哪个项目"，再查"审批状态"
行动：search_user_memory("项目 预算")
观察：返回3个项目的记忆，不确定用户指的是哪个
思考：需要更多上下文，缩小范围
行动：search_user_memory("项目 预算 最近 正在做")
观察：命中"自动驾驶项目"（上周刚讨论过）
行动：search_user_memory("自动驾驶项目 预算 审批")
观察：找到审批记录
回答："你的自动驾驶项目预算已于周三获批"
```

**工程决策**：
- 选择方案：使用 ReAct 模式，Agent 自主决策检索次数
- 理由：体现"智能体化"的核心价值
- 代价：多次检索 = 多次 LLM 调用 = 更高成本和延迟

## v0.4 验证集

**全量回归测试**：所有60个用例（20基础 + 20多会话 + 20主动服务）

**新增验证维度**：
- 知识更新准确性：当用户修正信息后，后续回答使用最新值
- 冲突消解：矛盾信息出现时，Agent 能区分适用场景
- 程序记忆利用：Agent 能识别用户的常规行为模式

## v0.4 验收标准

| 验收项 | 标准 |
|--------|------|
| Proposer-Reviewer | 审核通过的PR准确率 >95% |
| 全量回归通过率 | ≥85%（51/60） |
| 程序记忆 | 至少提炼出3个有效程序记忆 |
| 智能体RAG | Agent 在20%的用例中使用多轮检索 |

## v0.4 工程决策总结

| 决策点 | 选择 | 理由 | 备选方案 |
|--------|------|------|----------|
| 更新机制 | 异源Agent审核 | 保证知识准确性 | 单模型自动更新（风险高） |
| 记忆模型 | 双层：概览+细节 | 兼顾速度和深度 | 纯RAG（无概览） |
| 检索模式 | 智能体化RAG | 体现Agent自主性 | 固定流水线（v0.3） |
| 程序记忆 | 定期模式提炼 | 将经验结构化 | 仅保留情景记忆（无法复用） |
