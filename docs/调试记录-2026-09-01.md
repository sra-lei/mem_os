## 一、前端看板

### 1.1 用例列表表头与数据不对齐
- **现象**：`CasesTable` 通过率/操作列表头右对齐，单元格内容却靠左。
- **根因**：CSS 工具类 `.justify-end` 和 `.gap-6` **从未定义**（只有 `.flex/.items-center/.gap-8`），flex 默认 `justify-content: flex-start`。
- **修复**：`components.css` 补齐两个工具类。

### 1.2 运行次数列换行
- **现象**：表头"运行次数 ↕"被挤成两行。
- **根因**：列宽 `72px`，减去 th 左右 padding（各 16px）后仅 ~40px，容不下 4 个中文字 + 排序箭头。
- **修复**：列宽 `72px → 100px`，并为 `.table thead th` 加 `white-space: nowrap` 全局防换行。

### 1.3 数字与表头右边缘仍错位
- **现象**：表头文字右缘和单元格数字右缘始终差一个箭头宽度。
- **根因**：右对齐列表头渲染为 `运行次数 ↕`（箭头在文字右侧），箭头占位把文字向左推。
- **修复**：右对齐列排序箭头移到**文字左侧**（`↕ 运行次数`），并固定箭头宽度（12px）。

### 1.4 Setup Dialog 与会话历史素材重复
- **现象**：用例详情页两个区块展示相同内容。
- **根因**：`setup_dialog` 与 `conversation_histories_raw` 存的是**同一份 JSON**（历史兼容字段与语义字段同值）；顺带发现 `expected_answer` 与 `expected_behavior` 也同值。
- **修复**：全链路删除 `setup_dialog`（模型/schema/加载脚本/DB 列），前端去掉重复区块并重排；`expected_answer` 前端不再展示。

## 二、评测框架（testing）

### 2.1 Moonshot judge 429 限流
- **现象**：`openai.RateLimitError: request reached organization max RPM: 3`。
- **根因**：① 账号**每分钟最多 3 次请求**；② 用户加了 `retry_on_rate_limit` / `retry_on_status_code`——**不是 `OpenAI()` 的构造参数**，实例化即 `TypeError`；③ 重试退避等不到 60s 的 RPM 窗口。
- **修复**：移除无效参数、保留 `max_retries=3`；新增 `_throttle()` 保证调用间隔 ≥20s；重试耗尽兜底返回 `JudgeResult(error=...)` 不崩 runner。

### 2.2 Judge 的 ResponseFormatJSONSchema 构造错误
- **现象**：`ValidationError: json_schema Field required`。
- **根因**：`ResponseFormatJSONSchema(schema=JudgeResult)` —— 传了 dataclass，且参数名应为 `json_schema`。
- **修复**：改用标准 `response_format={"type":"json_schema", "json_schema":{"name":..., "schema":<dict>, "strict":true}}`。

### 2.3 Judge SYSTEM_PROMPT 语法/逻辑错误
- **现象**：f-string 里的 JSON 模板花括号触发 `ValueError: Invalid format specifier`。
- **根因**：`f'''...{...}'''` 与 `.format()` 混用，JSON 花括号未转义。
- **修复**：改普通字符串模板 + `{criteria}` 占位符，`.format()` 注入；补 `println`→`print`、`Json.loads`→`json.loads`、容错解析。

## 三、os_mem 记忆系统

### 3.1 循环导入
- **现象**：`ImportError: cannot import name 'MemoryProvider' from partially initialized module 'os_mem'`。
- **根因**：`os_mem/__init__ → provider → core → base_provider → from os_mem import MemoryProvider`（在初始化中反向导入）。
- **修复**：`provider.py` 延迟导入 `BaseProvider`（移到 `MemoryProvider` 定义后）；`base_provider.py` 用相对导入 `from ..provider import MemoryProvider`。

### 3.2 SQLModel 全局 metadata 串表
- **现象**：`memories.db`（记忆库）里出现 `test_runs` 等评测表；`memos.db` 里出现记忆表。
- **根因**：所有 `SQLModel` 表注册在同一个全局 `SQLModel.metadata`，两边的 `create_all()` 全量建表。
- **修复**：两库的 `init_db()` 都用 `create_all(engine, tables=[自己的表])` 限定。

### 3.3 记忆库 "unable to open database file"
- **现象**：首次写记忆库报 `sqlite3.OperationalError: unable to open database file`。
- **根因**：`MEMORY_DB_PATH="data/memories.db"`，`data/` 目录不存在，SQLite 不会自动建父目录；且 `init_db()` 从未被调用（表也没建）。
- **修复**：`get_engine()` 里 `mkdir(parents=True)`；`get_session()` 自动 `init_db()`；数据库路径锚定 `src/os_mem/`。

### 3.4 BM25 检索结果与查询无关
- **现象**：查询"checking account number"却返回姓名/地址等前三条消息，且**三条分数完全相同**。
- **根因**（多层）：
  1. `search_user_memories` 用 `enumerate(results, 1)` 的**序号**当文档索引，BM25 结果被忽略，固定返回前 3 条；
  2. `doc.count(w)` 是**子串计数**（"my" 命中 "myself"）；
  3. idf 缺 `log`；
  4. 无停用词过滤（what/my/it/set 干扰关键词权重）。
- **修复**：改用 BM25 返回的 `doc_idx`；split 后词频计数；标准 idf 公式；加停用词表。

### 3.5 ingest 只存 user 消息导致答案错误
- **现象**：检索命中 Wells Fargo 旧账号（8847293001）而非正确答案 FNB 账号（4429853327），DeepSeek 答错。
- **根因**：`save_user_memories` 只存 `role=="user"` 的消息，而**正确答案是 assistant（客服）告知用户的**，被过滤丢弃。
- **修复**：`role in ("user", "assistant")` 全量存储；并加"会话已存在则跳过"去重。

### 3.6 数据库迁移列错位
- **现象**：迁移后 `created_at` 列存进了 expected_answer 的文本，读取报 `Invalid isoformat string`。
- **根因**：新旧库 `test_case_definitions` **列顺序不同**（历史 ALTER 累积 vs 当前 models 定义），`INSERT ... SELECT *` 按位置错位。
- **修复**：清空错位数据，从 YAML 重灌（`load_test_cases`）；教训：迁移应**按列名**映射而非 `SELECT *`。

## 四、向量库（Milvus / pymilvus 3.0.1）

### 4.1 pymilvus 版本 API 差异
- **现象**：`ImportError: cannot import name 'AnnSearchRequest' from 'pymilvus.client.types'`；`'MilvusClient' object has no attribute 'get_collection'`。
- **根因**：装的是 **pymilvus 3.0.1**（不是 2.5.x）——`AnnSearchRequest/RRFRanker` 在**顶层**导出；`MilvusClient` 统计用 `get_collection_stats`（无 `get_collection`）。
- **修复**：`from pymilvus import AnnSearchRequest, RRFRanker`；`count()` 改用 `get_collection_stats` + `describe_collection` 兜底。

### 4.2 BM25 function 需要 analyzer
- **现象**：建 collection 报 `BM25 function input field must set enable_analyzer to true`。
- **根因**：full-text search 的输入文本字段必须启用 analyzer。
- **修复**：`fact` 字段加 `enable_analyzer=True, analyzer_params={"type":"standard"}`。

### 4.3 混合检索 filter 位置
- **现象**：pymilvus 3.0 的 `hybrid_search()` 顶层没有 `filter` 参数。
- **修复**：元数据过滤放到**每个 `AnnSearchRequest` 的 `filter=`**（dense + sparse 两路都带）。

### 4.4 混合检索方案（Milvus 2.5+ 能力）
- collection 新增 `sparse`（SPARSE_FLOAT_VECTOR）+ BM25 function（fact → sparse），sparse 建 `SPARSE_INVERTED_INDEX/BM25` 索引；
- `search(query_vector, query_text, ...)` 用 `hybrid_search([dense, sparse], ranker=RRFRanker())` 融合；
- `query_text=None` 时兼容单路稠密检索。

## 五、LLM 结构化提取（StructuredMemService）

### 5.1 `'LLMClient' object has no attribute 'chat'`
- **根因**：`os_mem` 的 `LLMClient` 只有 `__init__`，无 `chat`；调用方用 OpenAI 风格 `client.chat.completions.create(...)`。
- **修复**：`LLMClient` 加 `chat` property 返回底层 OpenAI client（链式 API 兼容）。

### 5.2 `MemoryFacts() argument after ** must be a mapping`
- **根因**：LLM 输出的是 **JSON 数组**（裸 list），`MemoryFacts(**data)` 的 `**` 需要 mapping。
- **修复**：`list` 时 `MemoryFacts(facts=data)`；dict 时 `**data`（兼容两种格式）。

### 5.3 `name 'logger' is not defined`
- **根因**：`_validate_response` 用了 `logger`，文件里只定义了 `_logger`。
- **修复**：`logger` → `_logger`。

### 5.4 提取返回空（`json.JSONDecodeError: Expecting value: line 1 column 1 (char 0)`）
- **根因**（逐步排查）：
  1. `response_format=json_object` 与 prompt 要求"输出数组"冲突（json_object 只保证对象）→ prompt 改 `{"facts":[...]}` 对象格式 + 解析清洗（去 markdown 代码块、空内容兜底）；
  2. `finish_reason=length` —— **输出被 `max_tokens=2048` 截断**，json_object 截断时 content 为空 → `DEEPSEEK_MAX_TOKENS` 调到 4096；
  3. **连续调用返回空 content**（deepseek-v4-flash 对长对话/连续调用不稳定，首调用正常、第二次起空）→ `complete()` 空返回重试（退避 3s/6s/9s）。

### 5.5 分段提取（长对话）
- **方案**：`_chunk_dialog()` 按消息分段，每段 < 2048 字符、段间重叠 5 条消息（冗余）；逐段 `_extract_chunk()` 提取，`_dedup_facts()` 按 `(category, key, value)` 去重；全部失败才降级存原始对话。

## 六、构建与部署

### 6.1 esbuild / Vite 构建在沙箱失败
- **现象**：`npm run build` 报 esbuild spawn EPERM。
- **根因**：esbuild 通过管道与子进程通信，被 DSH 文件沙箱拦截（workspace-write 模式）。
- **修复**：构建命令升级沙箱权限（`danger-full-access`）执行。

### 6.2 git push 到 GitHub
- **现象**：HTTPS 推送要求交互输入用户名（沙箱无法交互）；SSH 推送报 `does not appear to be a git repository`；`couldn't create signal pipe`。
- **根因**：① HTTPS 无凭据；② SSH remote URL 用了**斜杠**格式 `git@github.com/sra-lei/mem_os.git`（应**冒号** `git@github.com:sra-lei/mem_os.git`）；③ Git for Windows 的 sh.exe 在沙箱里无法建信号管道。
- **修复**：修正 URL 为冒号格式；`GIT_SSH_COMMAND=ssh` + 升级沙箱权限推送；移除多余的 `origin`（HTTPS）remote。

## 七、通用经验

1. **SQLModel 全局 metadata**：多库共存时必须用 `create_all(tables=[...])` 限定，否则表互相串建。
2. **数据库迁移**：跨结构迁移用**列名映射**，不要 `SELECT *`（列顺序变化会静默错位）。
3. **pymilvus 版本差异**：2.5 与 3.0 API 变化大（导入路径、方法名），先探测版本再写代码。
4. **LLM 返回不稳定**：json_object 模式与数组输出冲突、`max_tokens` 截断、模型连续调用空响应——排查顺序：先看 `finish_reason` / `usage`，再调整 prompt 格式与输出上限，最后加重试/退避。
5. **停用词与检索质量**：BM25 类检索必须过滤停用词 + 词频（非子串）计数，否则高频虚词干扰关键词。
6. **并行编辑冲突**：多进程/协作者同时改文件会互相覆盖——改动前先读最新版本，被覆盖后重新应用。
