# 方案：会话原文持久化 + 处理状态机 + 双轨编排（定稿）

日期：2026-09-04 · 状态：**设计收敛，分两批实施**（A 批已落地 / B 批待实现，见 §7）
关联：MemOs需求文档 v0.3（异步队列写入）；本仓库 struct/full/base 三 provider。

## 1. 目标（本次改动范围）

1. **会话原文必落库，不分 provider**：任何会话一经 ingest，原始 message 逐条
   持久化到 `conv_messages`（供审计、回溯、异步 worker 消费）。
2. **会话元数据 + 处理状态**：新增 `conv_meta` 对话元数据表（不含原文），顺带管理
   不可逆的处理状态；状态转移机保证一轮处理内单向推进。
3. **双轨编排**：full = 同步快速通道（登记 + 原文落库后 <1s 返回调用端，不调 LLM）；
   struct = 异步 worker 后台完成结构化入库（LLM 提取 → SQLite → 向量）。
   conv_meta 状态机兼任任务队列（状态 + 租约 + 重试），**零新依赖**（无 Redis/Celery，
   本机无 Redis 且资源受限）。
4. 会话级原子化 + 并发安全：仅 COMPLETED 跳过；非完成态「接着处理」；
   并发只允许一个执行者（CAS + 唯一约束 + 租约）。

## 2. 数据模型与职责

| 表 | ORM | 职责 | 说明 |
|---|---|---|---|
| `conv_meta` | ConversationMeta | 会话**元数据 + 处理状态**（唯一会话登记表，base/struct/full 共用） | user_id / source_session_id / message_count / started_at / ended_at / status / attempts / last_error / 时间戳；`UNIQUE(user_id, source_session_id)` |
| `conv_messages` | Message | 会话**原文**逐条落库（唯一权威原文表） | content=消息 JSON；contains_pii / masked_text（PII 标记）；**冲突键 `(user_id, source_session_id, seq)`，seq=会话内消息序号(0 起)**，写冲突按 §4.1 value 冲突逻辑处理；`previous_content` 归档旧值 |
| ~~conv_memories~~ | ~~ConversationMemory~~ | **已退役**（方案1 合并进 conv_meta） | 原 base 登记表：无唯一约束 + summary 死字段；base 读写已迁 conv_meta，表在 init_db 时删除 |
| `struct_memories` | StructuredMemory | struct 提取结果（facts） | 冲突按 (user_id, category, key) upsert |

**不变量**：原文只在 `conv_messages`；`conv_meta` 行与 `conv_messages` 行同生共死
（登记事务内一并写入，崩溃整体回滚无残留）。

### 2.1 双 provider 双写消息：不做互斥，用 value 冲突逻辑吸收

base(note provider) 与 struct/full 都可能写同一会话的原文到 `conv_messages`
（base 走 conv_memories 门禁、struct/full 走 conv_meta 门禁，两套登记互不感知，
**先当成两个会话处理**——不引入 provider 级互斥/统一登记）。消息层的重复/冲突
按 struct 的 value 冲突逻辑处理（镜像 `save_structured_memories_to_sqlite`）：

- 冲突键：`(user_id, source_session_id, seq)` —— seq 为消息在会话中的序号（0 起，
  与 struct facts 的 (user_id, category, key) 同构：会话=user 域、key=seq、value=content）；
- **后入的走记忆更新**：同键行已存在 → UPDATE 为新值（content / contains_pii /
  masked_text / create_at），**内容变化时旧值归档到 `previous_content`**；
  同键行不存在 → INSERT；
- **数据一致则无影响**：同键同值 UPDATE 无变化、不产生重复行 —— 两个 provider
  处理同一会话时消息集完全一致，结果幂等；
- 只增不删（与 struct facts 一致，不做 tombstone）：消息条数减少时旧尾行保留，
  如需清理后续单独设计。

> 老数据注意：`seq`/`previous_content` 为新增列，既有 conv_messages 行无 seq
> （默认 0 会撞唯一键）—— 上线时需一次性 backfill（按 rowid 序赋 seq）或清库重导。

## 3. 处理状态机（定稿）

```
PENDING ─► READY ─► EXTRACTING ─► SAVING_SQLITE ─► SAVING_VECTOR ─► COMPLETED
 (登记中)  (原文已落库,    (struct 处理中；每阶段开始前推进状态)
          待 struct)
活跃态 {PENDING, READY, EXTRACTING, SAVING_SQLITE, SAVING_VECTOR} 任一 ► FAILED（可重试）
```

规则：
1. 一轮处理内只沿合法边前进：无反向/跳级/终止态外出（同态 no-op 允许）；
   非法转移抛 `IllegalTransitionError`。
2. **每阶段开始前**推进状态 —— 崩溃时状态停留在最近开始的阶段，即故障定位点。
3. **COMPLETED = 唯一跳过态**；READY / FAILED 可被立即接管；中途态仅租约过期
   （`updated_at` 停更超 `CONV_LEASE_SECONDS`，默认 1800s，判定崩溃残留）可接管。
   跨轮重启只经 claim 的 CAS，不走状态机反向边。

## 4. 登记与并发（register / claim）

**`register()`（所有 ingest 的公共第一步）—— 单事务原子完成：**

1. INSERT `conv_meta`（status=PENDING）；唯一约束裁决并发插入；
2. 逐条 upsert 写 `conv_messages`（seq=序号，PII 标记复用 p2check；冲突按 §2.1）；
3. status → READY，提交。

→ 崩溃无残留；消息仅在登记时写一次，接管/重跑**不重写**（重启场景从库内
`conv_messages` 重建原文）。同 (user, session) 已 COMPLETED → register 返回 None（跳过）；
非完成态 → 视状态判定接管。

**worker 接管 `claim_ready()`（CAS）：** `UPDATE … SET status='EXTRACTING',
attempts=attempts+1, last_error='' WHERE id=? AND status=<观测值>`；
可取集合 = {READY, FAILED}（立即）+ 租约过期中途态。SQLite 单写者下并发接管
只有一个成功；多 worker / 多线程安全，无需额外锁。

## 5. 双轨编排

```
调用端 ingest(conversation, mode):
  mode=sync_full（生产默认，full provider）:
      register(...)                     # 原文落库 + READY，<1s 返回
      full 层保留近期会话于内存供即时响应（现状 retrieve 不变）
  mode=sync_struct（评测/需立即长期记忆，struct provider）:
      register(...)
      struct 全阶段同步执行（EXTRACTING→…→COMPLETED）
```

struct worker（新增，SQLite 即队列）：

```
循环（WORKER_POLL_SECONDS 默认 5s）:
  扫描 conv_meta 可取行（READY/FAILED/租约过期中途态）
  每行 CAS 接管 → 从 conv_messages 读原文重建 Conversation
  → struct 流水线（阶段推进沿状态机）→ COMPLETED；异常 → FAILED（下轮自动重试）
```

worker 形态：`python -m os_mem.worker` 独立进程，或 `start_bg_worker()` 进程内
daemon 线程（嵌入未来 API 服务）。日志走既有 logger。

检索融合（full 近期 + struct 长期）属应用层，另行设计，本期不做。

## 6. 失败语义与边界

- SQLite 与 Milvus 无跨库事务：SAVING_VECTOR 失败留下已落 SQLite 的事实 ——
  不自动回滚（SQLite 是权威源），标记 FAILED，下轮重跑整轮（upsert 幂等不重复）。
- 进程被 kill：状态停更 → 租约过期后被接管重跑；无人 ingest 则行保留供查询。
- sync_struct 与异步 worker 不得同会话并发（sync 一次跑完即 COMPLETED；中途崩溃
  由租约过期后 worker 接管或人工置 FAILED 立即重试）。
- base provider（v0.1）已并入 conv_meta（方案1 合并，2026-09-04）：读写迁 conv_meta、
  conv_memories 退役删除；base 只 ensure_registered + upsert 原文，**永不改处理状态**
  （状态机只由 struct 管线驱动）——base→struct / struct→base 任意先后正确。
- eval layer1/2/3 继续用同步 mode，评测语义不变。
- 运维快捷恢复：崩溃残留人工置 FAILED 后重跑，无需等租约。

### 10.1 术语速查表

| 我们做的事 | 业界术语 | 一句话 |
|---|---|---|
| 同会话重复投递直接跳过 | **幂等（Idempotency）** | 同一操作执行多次与一次结果相同 |
| `UNIQUE(user_id, source_session_id)` | **唯一约束 / 幂等键** | 数据库层面物理防重，兜底并发插入 |
| `UPDATE … WHERE status=观测值` | **乐观并发控制 / CAS（Compare-And-Swap）** | 不加锁，靠"条件更新影响行数"裁决谁赢 |
| updated_at 停更超时即可接管 | **租约（Lease）** | 持有者须"续租"证明自己活着，过期视为崩溃 |
| 中途态 ≠ 完成态 → 接着处理 | **At-least-once + 消费者幂等** | 消息至少投递一次；副作用靠幂等收敛 |
| conv_meta 状态行当任务队列 | **DB 即队列 / Outbox 风格** | 用业务表当队列，省一套消息中间件 |
| FAILED 下轮自动重试 | **重试 / 死信（Dead Letter）** | 失败不丢；持续失败需转人工 |
| 消息后入覆盖 + 旧值归档 | **LWW 冲突消解 + 版本痕迹** | 同一键最后写入者赢，旧值留档 |
| SQLite 先写、Milvus 后写 | **双写问题（Dual-write）** | 两个存储无跨库事务，无法原子提交 |

### 10.2 幂等（Idempotency）与幂等键

- **解决**：重放/重试/双 provider 都可能导致同一会话被处理多次。
- **业界**：API 网关层常用"幂等键"（如 Stripe 的 `Idempotency-Key` header）；DB 层最
  朴素可靠的就是**唯一索引**。分布式的做法常是"唯一索引 + 冲突捕获后按已有行处理"。
- **本项目**：`conv_meta.UNIQUE(user_id, source_session_id)` 兜底并发插入；
  `COMPLETED → 跳过` 是**业务幂等**，唯一约束是**物理幂等**，两层都在。
- **设计考量**：
  - 幂等的"键"怎么定：本项目=会话（user+session）。键范围错了要么挡不住重放，
    要么把两次正常的新会话误判成一次。
  - 插入冲突后怎么办：不能直接报错，要**重读已有行再决策**（我们 catch IntegrityError
    后按已有行重新走 claim 判定）。
  - 幂等 ≠ 永远不重跑：我们的设计是"完成态才跳过，非完成态接着做"——这比"存在即跳过"
    更接近消息系统的语义（见 10.5）。

### 10.3 乐观并发控制（CAS）vs 悲观锁 vs 分布式锁

- **解决**：多个执行者（多进程 worker/多线程）抢同一会话时不能双跑。
- **术语**：
  - **乐观锁（Optimistic Locking）**：不加锁，更新时带条件 `WHERE 版本=我读到的版本`，
    影响行数为 0 说明别人先改了 → 冲突。本项目状态字段本身就当"版本号"用
    （`UPDATE … WHERE status='FAILED'`，只有观测到 FAILED 的人能接管成功）。
  - **悲观锁**：`SELECT … FOR UPDATE`（先锁行再干活）。SQLite 是单写者，天然串行化，
    不常用 FOR UPDATE。
  - **分布式锁**：Redis SETNX + TTL / etcd lease，跨进程互斥。我们有 SQLite 唯一行 +
    CAS，省了这套。
- **设计考量**：
  - CAS 依赖"冲突是罕见的"才高效；若同一行高频竞争会大量空转重试。
  - 条件更新必须**带观测值进 WHERE**，否则读-改-写之间被插队就丢失更新（lost update）。
  - SQLite 单写者 + 事务让 CAS 语义天然成立；换 PostgreSQL/MySQL 也成立（行锁+MVCC），
    换成无事务的 KV 存储就要小心了。

### 10.4 租约（Lease）——区分"活着"与"死了"

- **解决**：进程崩溃后，它占着的"处理中"状态不能永远锁死会话（这就是为什么
  中途态要能被人接管）。
- **术语**：**Lease / Heartbeat / Visibility Timeout**（SQS 管可见性超时）；
  K8s/etcd 的选主租约是同一思想：持有者定期续租，不续 = 过期 = 可被接管。
- **本项目**：没有专门心跳线程，而是**每推进一个阶段就刷新 `updated_at`**（等于续租）；
  中途态超过 `CONV_LEASE_SECONDS`（默认 1800s）未动 → 判定崩溃残留，允许 CAS 接管。
  `READY`/`FAILED` 不需要租约（前者是"明确交棒"，后者是"明确失败"）。
- **设计考量**：
  - **租约时长必须大于单个阶段最长耗时**，否则会误抢还活着的任务（LLM 提取一个超长
    会话可能几分钟——所以默认值给 30 分钟，且可 env 调）。
  - 续租粒度：阶段推进即续租已够用；若存在"单个阶段内长时间无状态变化"，需内部心跳。
  - 接管不是零代价：崩溃发生在"已写一半"时，重跑要靠下游幂等收敛（见 10.6）。

### 10.5 状态机（FSM）与 DB 即队列

- **解决**：把"会话处理到哪了"变成可校验、可审计、不可乱跳的显式状态。
- **业界**：**有限状态机（Finite State Machine）**——枚举状态 + 合法转移表，
  非法转移直接报错（我们 `IllegalTransitionError`）。常用于订单、审批流、任务调度。
- **DB 即队列 / Outbox**：把状态行本身当任务队列（worker 扫"可取状态"），
  好处是**零新依赖**（不引 Redis/Celery，本机也没 Redis）；业务表与队列状态天然同库
  同事务（这就是 **Outbox Pattern** 的核心动机：业务写库和"要发的事件"写在同一事务，
  避免双写不一致）。代价是**轮询**有延迟和空转。
- **本项目**：状态机管"一轮处理内单向前进"；"整轮重启"不反向走状态机，而是由 claim
  的 CAS 直接置回 EXTRACTING——**状态机只管运行内，重跑入口只有门禁一个**。
  若允许任意处回退，状态机会退化成没人信的自由字符串。
- **设计考量**：
  - 状态枚举要"完备且互斥"：每个状态回答"现在到哪一步 / 谁能碰 / 下一步去哪"。
  - 所有状态变更必须走同一道门（本项目 = service 的 mark/claim），禁止散落 UPDATE。
  - 队列语义：**At-least-once**（崩溃重投）→ 消费者必须幂等 → 整体效果接近
    exactly-once（术语：effective once）。

### 10.6 幂等消费 + LWW 冲突消解 + 只增不删

- **解决**：base 与 struct 都写 conv_messages，同一会话两遍 → 重复行"打架"。
- **术语**：
  - **Idempotent Consumer**：消费端靠键去重，重复投递无副作用。
  - **Upsert / Last-Write-Wins（LWW）**：同键冲突时"后写覆盖先写"，是分布式系统最
    常用的冲突消解；缺点是丢信息——所以搭配**旧值归档**（近似"版本留痕"，
    完整做法是 `version` 列自增或独立审计/事件表）。
  - **Append-only / 无 tombstone**：只增不删，便于审计，靠状态/版本表达"当前值"。
- **本项目**：冲突键 `(user_id, source_session_id, seq)`（seq=消息在会话中的序号）；
  同键同值 → no-op（一致无影响）；不同值 → 覆盖 + `previous_content` 归档。
- **设计考量**：
  - **冲突键是灵魂**：seq（位置）适合"同一对话新旧两版"；content hash 适合"内容级
    去重"；业务键适合"事实级合并"（struct 用 category+key）。选错键 = 该合的没合 /
    不该合的误覆盖。
  - LWW 依赖"后写=更新"，若时钟乱序（多机时间不同步）后写可能其实是旧写——
    严格做法是带单调递增版本号比较，而不仅靠写入顺序。
  - 覆盖有损：previous_content 只留一版；要完整历史得上审计表/事件溯源（Event Sourcing）。
  - 只增不删的代价：数据膨胀与"删除语义"缺失，需要时可加墓碑（tombstone）行。

### 10.7 双写问题（Dual-write）与"本地为权威、云端可重建"

- **解决**：一条事实既要落 SQLite（struct_memories）又要写 Milvus 向量库，
  两个存储之间**没有跨库事务**（2PC 不现实），怎么保证不丢不错。
- **术语**：**Dual-write problem**——任何"同一数据写两个系统"都有此问题；
  常见出路：2PC（重）、Saga/补偿（复杂）、**Outbox**（先本地落库+事件表，异步投递）、
  **主从式重建**（一个权威，另一个随时可从权威重建）。
- **本项目**：顺序固定"**SQLite 先写（权威源）→ Milvus 后写**"；Milvus 失败不回滚
  SQLite，只把会话标 FAILED，下轮重跑靠 upsert 收敛；设计上 Milvus 随时可从 SQLite
  全量重建（"向量库重建兜底"注释）。Milvus 里的行用随机 uuid、靠 (user,key) 与本地
  对应，天然适合"清了重建"。
- **真实教训（今天踩过）**：Milvus 里 1370 条评测向量，本地 struct_memories 却是空的
  ——云端成了**孤儿数据**（无本地副本、无法重建）。反例正好说明：双写系统必须
  "**权威在本地且可重建**"，否则远端即深渊。
- **设计考量**：
  - 先写谁？先写权威、后写易重建方；失败时权威已落 → 可重试不丢。
  - 消费方要幂等（Milvus 写入按 (user,key) 语义收敛，不重复）。
  - 定期对账（reconcile）：权威与从库行数/内容核对，把"对不上"暴露成可观测问题。

### 10.8 重试 / 死信（Retry / Dead Letter）

- **解决**：LLM 调用、向量库都可能临时失败，不能丢会话。
- **术语**：失败重投 + **指数退避（exponential backoff）+ 抖动（jitter）**；
  反复失败的"毒丸消息"（poison message）应进**死信队列**转人工，而不是无限重试。
- **本项目**：FAILED 会话下轮即被接管重跑（无退避、无次数上限），`attempts` 只做观测。
- **设计考量（本项目待改进点，诚实列出）**：
  - 无限重试：若某会话必然失败（如数据格式毒丸），会每轮白烧 LLM 费用 → 建议加
    `max_attempts`（如 3），超限不再自动接管，转人工（运维置 FAILED 手动重跑或删行）。
  - 退避：连续失败应拉长间隔，避免 worker 空转同一行。
  - attempts 已可观测（conv_meta.attempts），加阈值只是几行代码，B 批排期时一并考虑。

*学习主线建议：幂等 → 租约 → CAS 是"并发与重试三件套"，通常一起出现（本项目的 claim
就是三者的合体）；状态机与 DB 即队列解决"可观测 + 零依赖调度"；LWW/Outbox/权威重建
解决"多存储一致"。这套组合是任务型系统（爬虫调度、异步导入、消息处理）的通用骨架。*
