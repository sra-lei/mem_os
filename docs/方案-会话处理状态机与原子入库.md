# 方案：会话原数据表 + 处理状态机（struct 入库原子化）

日期：2026-09-04 · 状态：✅ 已实现（commit 见文末执行记录） · 范围：struct provider 入库链路

## 1. 背景与问题

当前 `StructProvider.ingest`（→ `StrucMemService.add_structured_memory`）对每个会话
无差别全量执行：LLM 分段提取 → 数字兜底 → SQLite `struct_memories` 落库 → 向量化 →
Milvus 写入。缺陷：

1. **无会话级幂等**：同一会话被重复投递（重放、cron 补跑、多实例并发、评测重跑）会重复
   触发整条昂贵的 LLM 提取链路，事实重复写入（虽有 `(user_id, category, key)` upsert
   兜底，但每次仍白跑 LLM 与向量化）。
2. **不可观测**：会话处理到哪一步、是否已入库、失败原因，均无记录；`struct_memories`
   只存提取后的事实，**会话原数据不落库**，出问题无法回溯原文。
3. **非原子**：检查与登记之间无事务边界，也没有「先登记后干活」的门禁。

## 2. 目标

- 新增一张表，保存**会话原数据 + 处理状态**，作为 struct 入库的会话级账本（ledger）。
- struct 入库**会话级原子化**：入库前先检查该会话是否已登记/已入库 —— 已有则整体跳过，
  不再进入后续任何流程。
- 没有则**先登记（初始状态）**，之后**每个流程阶段开始前先推进处理状态**。
- 会话状态**不可逆** → 引入状态转移机，所有状态变更必须沿合法边前进，杜绝回退/跳级。

## 3. 设计

### 3.1 新表 `conv_process`

| 列 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | uuid hex |
| user_id | TEXT, idx | 归属用户（= eval case_id / 生产 user_id） |
| source_session_id | TEXT, idx | 会话外部 ID（`conversation.source_session_id`） |
| status | TEXT, idx | 当前处理状态，见 3.2 |
| raw_payload | TEXT | 会话原数据（messages 列表的 JSON 原文），审计/回溯用 |
| last_error | TEXT | FAILED 时的错误摘要 |
| created_at / updated_at | DATETIME | 登记时间 / 最近状态变更时间 |

**唯一约束 `UNIQUE(user_id, source_session_id)`**：DB 层兜底防重 —— 即使并发/进程竞争
穿透了业务检查，第二个插入也会因唯一约束失败而整体跳过（SQLite 单写者 + 唯一索引 =
原子性双保险）。

DDL：

```sql
CREATE TABLE conv_process (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL,
    source_session_id TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'PENDING',
    raw_payload TEXT NOT NULL DEFAULT '',
    last_error TEXT NOT NULL DEFAULT '',
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    UNIQUE (user_id, source_session_id)
);
CREATE INDEX idx_conv_process_status ON conv_process(status);
```

### 3.2 状态机（不可逆，线性前进）

状态与边（进程内代码即单一事实源，按阶段顺序自动生成链条）：

```
PENDING(初始/已登记)
   └─► EXTRACTING       开始 LLM 分段提取前
         └─► SAVING_SQLITE   开始 struct_memories 落库前
               └─► SAVING_VECTOR  开始向量化+Milvus 写入前
                     └─► COMPLETED  全部完成（终止态）
活跃态 {PENDING, EXTRACTING, SAVING_SQLITE, SAVING_VECTOR} 任一 ► FAILED（终止态，异常）
```

规则：

1. 只允许沿合法边前进；**无反向边、无跳级、终止态（COMPLETED/FAILED）无出边**。
2. **每个阶段「开始前」先推进状态**：若进程在阶段中途被杀/崩溃，状态停留在最近开始的
   阶段 → 状态即故障定位点。
3. `FAILED` 为终止态：**不自动重试、不回到初始态**（会话一次性处理语义）。
   补偿手段 = 运维人工删除该行后整会话重跑（事实写入按 `(user_id, category, key)`
   upsert，重跑天然幂等，不产生重复行）。
   > 若未来需要自动重试，扩展方向是「attempt 版本化」而非状态回退，本期不做。

### 3.3 原子登记（claim）

`claim(user_id, source_session_id, raw_payload)` 在同一事务内：

1. SELECT 是否存在该 `(user_id, source_session_id)` 行；
2. 存在（**任意状态**，含 COMPLETED/FAILED）→ 返回 None = 跳过，不改动任何状态（不可逆）；
3. 不存在 → INSERT 行（status=PENDING + 原数据）→ commit → 返回记录。
   唯一约束冲突（理论上被步骤 2 挡住）→ 捕获 IntegrityError 按跳过处理。

### 3.4 接入点与阶段推进

`StructProvider.ingest(conversation)` 编排：

```
proc = conv_process_service.claim(user_id, session_id, json.dumps(messages))
if proc is None:  log("会话已处理过，跳过") ; return
try:
    service.add_structured_memory(conversation, on_stage=marker)  # 阶段回调
    conv_process_service.mark(proc, COMPLETED)
except Exception as e:
    conv_process_service.fail(proc, e)   # 置 FAILED + last_error，然后 re-raise
```

`add_structured_memory(conversation, on_stage=None)` 在内部三处调用 `on_stage(...)`：
提取前 `EXTRACTING`、SQLite 落库前 `SAVING_SQLITE`、向量写入前 `SAVING_VECTOR`。
`on_stage=None`（默认）＝ 旧行为，不引入追踪（保持函数可独立复用/兼容其它调用方）。

### 3.5 失败语义与一致性边界（如实说明）

- SQLite 事实落库本身是单事务；但 SQLite 与 Milvus **无跨库事务**：
  `SAVING_VECTOR` 失败会留下已落 SQLite 的事实。处理策略：不自动回滚 —— SQLite
  是权威审计源（双写设计初衷），仅将会话标记 FAILED 供人工裁定，重跑整体幂等。
- 进程被 kill（非异常路径）时状态停在最近阶段，无法自动置 FAILED —— 属可接受边界，
  由状态值本身提供故障定位；人工处理同上。

## 5. 测试计划（全部无 LLM / 无 Milvus，走临时 sqlite）

1. 状态机：合法链 EXTRACTING→…→COMPLETED 全通过；非法转移（回退/跳级/终止态外出）
   → 报错；FAILED 可从任一活跃态到达。
2. claim：首登返回记录(status=PENDING)且原数据入库；同 (user, session) 二次 claim →
   None 且行数不变；不同 session 可各自登记。
3. provider 编排（monkeypatch 掉真实 service）：首次 ingest 状态走到 COMPLETED；
   重复 ingest 直接跳过、不再调用 add_structured_memory；异常路径 → FAILED + last_error。
4. 回归：`test_struct_mem_extract.py` / `test_struct_mem_sqlite.py` 不受影响。

## 6. 不做的事（本期范围外）
