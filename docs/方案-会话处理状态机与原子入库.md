# 方案：对话元数据表（conv_meta）+ 处理状态机（struct 入库原子化）

日期：2026-09-04 · 状态：✅ 已实现（v2 已按评审修正落地） · 范围：struct provider 入库链路

## 1. 背景与问题

当前 `StructProvider.ingest`（→ `StrucMemService.add_structured_memory`）对每个会话
无差别全量执行：LLM 分段提取 → 数字兜底 → SQLite `struct_memories` 落库 → 向量化 →
Milvus 写入。缺陷：

1. **无会话级幂等**：同一会话被重复投递（重放、cron 补跑、多实例并发、评测重跑）会重复
   触发整条昂贵的 LLM 提取链路，事实重复写入（虽有 `(user_id, category, key)` upsert
   兜底，但每次仍白跑 LLM 与向量化）。
2. **不可观测**：会话处理到哪一步、是否已入库、失败原因，均无记录。
3. **非原子**：检查与登记之间无事务边界，也没有「先登记后干活」的门禁。

## 2. 目标

- 新增一张**对话元数据表**：保存会话元数据（来源、消息数、起止时间等），
  **顺带管理处理状态**。会话原文（messages）**不存这张表** —— 逐条消息有专门的
  `conv_messages` 表承担，避免超长对话整段 JSON 落进元数据行带来的膨胀/读放大风险。
- struct 入库**会话级原子化**：入库前先检查该会话处理状态 ——
  **已完成（COMPLETED）→ 跳过**后续全部流程；
  **非完成态（未处理 / 失败 / 崩溃残留）→ 接着处理**（重启该会话的入库流程）。
- 处理状态**不可逆** → 状态转移机：一轮处理内只允许沿合法边前进，
  杜绝回退/跳级；新一轮处理（重启）由门禁统一接管，不破坏单向性。
- 并发安全：多个执行者同时处理同一会话时，**只有一个真正执行**。

## 3. 设计

### 3.1 新表 `conv_meta`（对话元数据表）

| 列 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | uuid hex |
| user_id | TEXT, idx | 归属用户（= eval case_id / 生产 user_id） |
| source_session_id | TEXT, idx | 会话外部 ID（`conversation.source_session_id`） |
| message_count | INT | 元数据：消息条数 |
| started_at / ended_at | DATETIME | 元数据：会话起止时间 |
| status | TEXT, idx | 处理状态，见 3.2 |
| attempts | INT | 重启次数（0 = 首次处理；每次接管重启 +1） |
| last_error | TEXT | FAILED 时的错误摘要（重启时清空） |
| created_at / updated_at | DATETIME | 登记时间 / 最近状态变更时间 |

**唯一约束 `UNIQUE(user_id, source_session_id)`**：同一会话只允许一行 —— DB 层兜底
防重（并发插入只有一个成功）。

> 命名与职责：这是「对话元数据表」，处理状态是顺带管理的字段，不是独立的处理账本。
> 会话原文逐条消息存 `conv_messages`（本项目已有）；若后续需要 struct 路径也保留
> 逐条原文，接入该表即可（本期不做，避免与 note/base 路径的写入语义冲突）。

DDL：

```sql
CREATE TABLE conv_meta (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL,
    source_session_id TEXT NOT NULL,
    message_count INTEGER NOT NULL DEFAULT 0,
    started_at DATETIME,
    ended_at DATETIME,
    status TEXT NOT NULL DEFAULT 'PENDING',
    attempts INTEGER NOT NULL DEFAULT 0,
    last_error TEXT NOT NULL DEFAULT '',
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    UNIQUE (user_id, source_session_id)
);
CREATE INDEX idx_conv_meta_status ON conv_meta(status);
```

### 3.2 状态机（一轮处理内不可逆，线性前进）

```
PENDING(初始/已登记)
   └─► EXTRACTING       开始 LLM 分段提取前
         └─► SAVING_SQLITE   开始 struct_memories 落库前
               └─► SAVING_VECTOR  开始向量化+Milvus 写入前
                     └─► COMPLETED  全部完成（终止态）
活跃态 {PENDING, EXTRACTING, SAVING_SQLITE, SAVING_VECTOR} 任一 ► FAILED（异常终止）
```

规则：

1. 一轮处理内只允许沿合法边前进：**无反向边、无跳级、终止态无出边**（同态 no-op 允许，
   用于「接管后首个阶段标记重复上报」）。非法转移抛 `IllegalTransitionError`。
2. **每个阶段「开始前」先推进状态**：进程在阶段中途崩溃 → 状态停留在最近开始的阶段，
   状态即故障定位点。
3. `FAILED` / 崩溃残留的 PENDING / 中途状态都**不是终点** —— 下一次 ingest 会经
   claim 门禁「接着处理」（见 3.3）。状态机的单向约束针对**同一轮处理**；
   跨轮重启由 claim 的 CAS 接管统一实现，不走状态机反向边。

### 3.3 原子登记 / 接管（claim）—— 非完成态接着处理

claim 的判定与并发控制（`conv_meta_service.claim`）：

| 现状 | 结论 | 并发手段 |
|---|---|---|
| 会话不存在 | **插入一行**（PENDING + 元数据），本调用负责处理 | 唯一约束：并发插入只有一个成功，败者按已存在重判 |
| status = COMPLETED | **跳过**（真正"已入库完成"） | — |
| status = FAILED | **立即接管重启**（attempts+1，清空 last_error，状态 → EXTRACTING） | 单语句 CAS 条件更新 |
| PENDING / 中途态，且行「过期」 | **接管重启**（同上）—— 判定为崩溃残留 | 同上 |
| PENDING / 中途态，租约未过期 | **跳过**（他人正在处理中） | 同上 |

**并发风险与对策**：

- **CAS（Compare-And-Swap）**：接管 = 一条 `UPDATE … SET status='EXTRACTING',
  attempts=attempts+1 WHERE id=? AND status=<观测值>`。SQLite 单写者下，两个并发
  接管只有一个匹配到行 —— 天然只有一个执行者进入处理，另一个本次跳过。
- **租约窗口**：中途状态若未过期（默认 `CONV_LEASE_SECONDS=1800`，env 可调），
  视为**活着**的处理者，不允许抢占；超过窗口未推进（updated_at 陈旧）判定为
  进程崩溃残留，允许接管。窗口需大于单个最长阶段耗时（LLM 提取），避免误抢活任务。
- **唯一约束**：兜底并发插入。
- 同进程多线程与跨进程多 worker 场景都被 CAS + 租约覆盖，无需额外分布式锁。
- 运维快捷恢复：崩溃残留想立即重跑，人工把行状态置 `FAILED` 再 ingest 即可
  （无需等租约过期）。

### 3.4 接入点与阶段推进

`StructProvider.ingest(conversation)` 编排：

```
meta = conv_meta_service.claim(user_id, session_id, message_count=…,
                               started_at=…, ended_at=…)
if meta is None:  log("已完成或处理中，跳过") ; return
try:
    service.add_structured_memory(conversation, on_stage=marker)  # 阶段回调
    conv_meta_service.mark(meta.id, COMPLETED)
except Exception as e:
    conv_meta_service.fail(meta.id, e)   # 置 FAILED + last_error，然后 re-raise
```

`add_structured_memory(conversation, on_stage=None)` 在内部三处调用 `on_stage(...)`：
提取前 `EXTRACTING`、SQLite 落库前 `SAVING_SQLITE`、向量写入前 `SAVING_VECTOR`。
`on_stage=None`（默认）＝ 旧行为，不引入追踪（保持函数可独立复用）。

### 3.5 失败语义与一致性边界（如实说明）

- SQLite 事实落库本身是单事务；但 SQLite 与 Milvus **无跨库事务**：
  `SAVING_VECTOR` 失败会留下已落 SQLite 的事实。处理策略：不自动回滚 —— SQLite
  是权威审计源（双写设计初衷），仅将会话标记 FAILED；下次 ingest 重启整轮
  （提取/落库按 `(user_id, category, key)` upsert，重跑天然幂等不重复）。
- 进程被 kill（非异常路径）时状态停在最近阶段、updated_at 停更 → 租约过期后被
  后续 ingest 接管重跑；若无人再 ingest，行保持原状供人工查询定位。

## 5. 测试计划（全部无 LLM / 无 Milvus，走临时 sqlite）

1. 状态机：合法链全通过；回退/跳级/终止态外出/未知状态 → 报错；同态 no-op 允许；
   FAILED 可从任一活跃态到达。
2. claim：首登 PENDING + 元数据入库；COMPLETED → 跳过；FAILED → 立即重启
   （attempts+1、清空 last_error）；中途态未过期 → 跳过（处理中）；过期（租约）
   → 接管重启；不同 (user, session) 互不影响；空 id 报错。
3. provider 编排（monkeypatch 掉真实 service）：首次 ingest → COMPLETED；重复 →
   跳过（不再调用 add_structured_memory）；异常 → FAILED + last_error；
   再次 ingest 重启直到 COMPLETED（attempts 递增）。
4. 回归：`test_struct_mem_extract.py` / `test_struct_mem_sqlite.py` 不受影响。
