# 《AI Agent 开发实战》第三章 阅读笔记：用户记忆与知识库

## 一、核心主题与框架

本章解决的核心问题：**如何让 Agent 在对话结束后仍然记住用户、记住知识**，实现从单次会话上下文管理到跨会话持久化知识体系的跨越。

### 1.1 两大知识尺度
- **用户记忆**：针对单个用户的个性化记忆（偏好、习惯、需求），让 Agent 成为“懂你的助手”
- **知识库**：面向所有用户共享的集体知识（法规、流程、专业文档），让 Agent 成为“领域专家”
- **共同点**：共用底层技术（向量检索、知识压缩），面临同样挑战（信息冲突、知识过期、检索不准）

## 二、用户记忆系统

### 2.1 用户记忆的工作原理
- **不保存每句对话**，而是用额外的 LLM 调用提取、压缩并审查对未来有用的事实
- **提取规则**：选择性（丢弃短期细节）、抽象化（归纳为长期偏好）、结构化（用可检索字段保存）

### 2.2 记忆能力评估：三层次框架
> 基于 LoCoMo 基准（平均 300 轮、最多 35 个会话）及商业实践归纳

| 层次 | 能力要求 | 具体表现 |
|------|----------|----------|
| **第一层：基础回忆** | 准确存储和检索直接提供的结构化信息 | 如“我的会员号是 12345”，后续精确返回 |
| **第二层：多会话检索** | 跨不同对象、不同时期的会话检索并推理 | 两辆车预约保养时找出全部信息并询问；区分有效合同与历史报价；旅行作为复合事件关联所有预订 |
| **第三层：主动服务** | 综合多会话、久远信息，提供预见性主动帮助 | 预订国际航班时关联护照信息，发现过期预警；手机损坏时整合所有保障方案；报税季主动整合所有税务文件 |

### 2.3 记忆的层次结构（放哪里）

| 层次 | 定义 | 特性 | 用途 |
|------|------|------|------|
| **轨迹（Trajectory）** | 单次运行的完整历史（用户消息+模型回复+工具结果） | 按时间顺序追加，只增不改（append-only） | 提供即时上下文 |
| **用户长期记忆** | 跨会话提炼的稳定信息 | 会被反复改写、合并、淘汰 | 跨会话个性化和连续性 |
| **业务状态** | 开发者定义的高层状态抽象 | 表示任务逻辑阶段（澄清中、处理中、等待付款等） | 事件驱动架构（第六章） |

### 2.4 四种存储格式（怎么存）

| 格式 | 特点 | 优势 | 劣势 |
|------|------|------|------|
| **Simple Notes** | 最小不可分事实（如“用户邮箱：john@example.com”） | 开销极低，O(1) 操作 | 信息关联性丢失，需重新拼凑 |
| **Enhanced Notes** | 完整上下文段落 | 保留叙事结构，语义完整 | 存储冗余，更新复杂 |
| **JSON Cards** | 三层嵌套结构（类别→子类别→键值对） | 支持部分更新，可预测可扩展 | 刚性结构，无法处理多维属性 |
| **Advanced JSON Cards** | 加入 backstory、person、relationship、timestamp | 解决实体消歧问题 | 生成和维护成本高 |

**实践选择标准**：
- 关键少量数据（用户偏好、关键人物关系）→ Advanced JSON Cards
- 大量非关键对话事实 → Simple Notes
- 多数生产系统 → **混合模式**（同 Agent 内不同类别走不同路径）

### 2.5 可执行代码作为知识表示（进阶）
- 将用户状态改为**带类型的可执行对象**，规则写成普通函数
- 借鉴“预写日志 + 检查点”机制：事实追加到日志，定期重建带类型状态
- **优势**：聚合、冲突检测、约束执行交给确定性函数，而非 LLM“心算”

### 2.6 认知科学基础（存什么）
三种记忆类型与 Agent 的对应关系：

| 认知类型 | 定义 | Agent 对应 | 示例 |
|----------|------|------------|------|
| **情景记忆** | 具体事件和经历 | 记录具体事件的时间、对象、细节 | “用户订了下周五去东京的 ANA 航班” |
| **语义记忆** | 抽象出的一般性知识 | 从多次交互提炼的稳定特征 | “用户是素食者”、“偏好靠窗座位” |
| **程序记忆** | 行为模式和流程 | 从反复行为中学到的通用流程 | 订机票的标准化流程 |

> **三套分类体系正交**：记忆层次（存在哪里）、存储格式（怎么存）、认知类型（存什么）可自由组合

### 2.7 记忆框架案例

#### Mem0 的演进
- **v2（写入时消歧）**：LLM 在 ADD/UPDATE/DELETE/NOOP 中决策，写入时消除冲突
  - 风险：错误更新会不可逆丢失历史，需二次 LLM 判断
- **v3（检索时推理）**：仅追加写入（ADD），冲突事实带时间信息并存；查询时融合语义相似度、BM25 关键词、实体匹配和时间排序
  - 优势：避免历史丢失，减少 LLM 调用，LoCoMo 从 71.4 提升到 92.5

#### Memobase
- **用户画像（Profile）**：可配置槽位，按主题-子主题两级组织
- **事件记忆（Event Memory）**：按时间线记录，回答时间相关问题
- **工程策略**：缓冲批处理（对话积累到规模或时限后再触发提取），摊薄 LLM 成本

### 2.8 记忆压缩与整理机制
1. **第一层：重要性评分筛选**（访问频率、时间衰减、情感强度、信息独特性）
2. **第二层：聚类** → 相似记忆分组生成代表性摘要（原始详细记忆存档到二级存储）
3. **第三层：抽象和泛化** → 从情景记忆提取一般性规律，转化为语义/程序记忆

### 2.9 隐私保护：日志脱敏
- 基于本地小模型（Qwen3 0.6B）检测 PII，而非云端 API（避免发送敏感数据）
- 识别结构化信息（身份证、银行卡）、半结构化信息（地址）、自然语言敏感内容
- **混合策略**：正则快速过滤明显模式 + LLM 深度分析剩余文本（召回率 95%+）

## 三、RAG 基础：知识获取管道

### 3.1 RAG 核心流程
**检索（Retrieval）→ 增强（Augmentation）→ 生成（Generation）**

### 3.2 文档分块（Chunking）
- **分块原因**：嵌入模型长度限制；避免整篇文档向量混杂多个主题
- **三种策略**：
  1. **固定大小切分**：按 token 数切分，保留重叠（10%-20%）
  2. **递归/结构感知切分**：按章节标题、段落、句子等自然边界递归切分（最常用默认选择）
  3. **语义切分**：计算相邻句子嵌入相似度，在“断崖”处切分（质量高，需额外计算）
- **块大小权衡**：太小（语义模糊） vs 太大（多主题混杂，检索精度下降）
- **常见起点**：256-1024 token，重叠 10%-20%

### 3.3 稠密嵌入（Dense Embedding）
- **核心思想**：将文本映射到向量空间，语义相近则向量距离近
- **余弦相似度**：衡量向量方向一致性（而非长度）
- **演进**：Word2Vec（静态，无法处理一词多义）→ BERT、BGE-M3（上下文感知，同一词不同语境有不同向量）
- **新特性**：BGE-M3 支持多语言与长文本输入

### 3.4 ANN 索引算法对比

| 特性 | ANNOY（基于树） | HNSW（基于图） |
|------|----------------|----------------|
| 构建速度 | 快 | 较慢 |
| 内存占用 | 低 | 较高 |
| 增量更新 | 不支持（需完全重建） | 支持（但长期需定期重建） |
| 查询精度 | 较高 | 极高 |
| 适用场景 | 静态数据集 | 动态实时索引 |

### 3.5 稀疏嵌入（Sparse Embedding）
- **核心**：精确的关键词匹配，基于词袋模型
- **演进**：TF-IDF → **BM25**（修正词频饱和与长度归一化）
- **BM25 公式要素**：k₁ 控制词频饱和速度，b 控制长度归一化强度
- **倒排索引**：从词到文档的反向映射表，实现快速定位
- **优势**：精确匹配（技术代码、人名查询表现佳）
- **劣势**：读不懂同义表达（搜“kitty”找不到“cat”）

### 3.6 混合检索与重排序
- **并行检索**（稠密 + 稀疏）→ **结果融合** → **神经重排序**
- **RRF（倒数排名融合）**：只看排名不看原始得分，综合得分 = Σ 1/(k + rank)
- **重排序器（Cross-Encoder）** vs **双编码器（Bi-Encoder）**：
  - 双编码器：独立生成向量，速度快，适合初步筛选
  - 跨编码器：拼接查询和文档深度比对，精度更高，适合精排
- **三个核心指标**：
  - **recall@k**（召回率@k）：正确答案出现在前 k 个结果中的比例（最贴近 RAG 需求）
  - **MRR**（平均倒数排名）：第一个相关文档排名的倒数平均
  - **nDCG**（归一化折损累积增益）：综合所有相关文档的排名与相关程度

## 四、超越扁平文本：知识组织与检索

### 4.1 结构化索引

#### RAPTOR（树状层次索引）
- 自下而上的递归抽象：叶子节点（文本块）→ 聚类 → 父节点摘要 → 根（高度概括）
- **适用场景**：从概念逐步钻进细节的查询（如“从整体架构到具体指令”）
- **优势**：多抽象层次检索，既能精确回答细节，也能提供宏观理解

#### GraphRAG（知识图谱）
- 基于三元组（实体-关系-实体）构建知识网络
- **核心优势**：
  1. **多跳关系推理**：沿关系边遍历（如“我的医生所在医院的地址”）
  2. **实体消歧**：区分同名实体（张医生-A vs 张医生-B）
- **局限**：自然语言转三元组导致语义降级（条件逻辑、时间依赖丢失）
- **适用场景**：医疗问诊、法律分析、家族关系管理等垂直领域

> **选择判断标准**：查询主要是“找到包含某信息的文档片段”→ 混合检索够用；查询经常需要跨文档综合或多层次导航 → 结构化索引才值得投入

### 4.2 文件系统范式（OpenViking）
- 将所有上下文映射为虚拟文件系统中的目录和文件，唯一 URI
- **L0/L1/L2 三层按需加载**：
  - L0（摘要，~100 tokens）：判断目录相关性
  - L1（概览，~2000 tokens）：规划决策
  - L2（全文）：需要深入时按需加载
- **关键前提**：文件间必须建立链接与索引（横向关联），形成双向可达引用网络

### 4.3 知识更新机制

#### 增量更新（PR 模式）
1. **Proposer Agent 提交 PR**：从证据中发现新事实，在工作分支上提交 diff
2. **Reviewer Agent 独立审核**：检查证据支持性、冲突、遗漏
3. **双方迭代收敛**（设最大迭代次数）
4. **合入后 CI 检查**：格式、链接、元数据；重建向量索引

**关键原则**：
- Proposer 和 Reviewer 使用能力相近但不同家族的模型（如 Claude + GPT），降低同源错误
- 权限强制分工：Proposer 只能写工作分支，Reviewer 只读证据
- 原始证据层（只增不改）、知识层（可修订）、服务层（从版本生成的索引）三层分离

#### 定期整理
1. **去重、去旧与合并**：删除、归并或重写语义重复的条目
2. **回到原始数据核查**：检查摘要是否遗漏关键事实、丢失否定词或时间条件
3. **冲突解决与场景限定**：追溯各自信息源，若都有效则标注适用场景而非强行删除
4. **失效内容检测与下线**：附加版本号、生效/失效时间元数据，检索时过滤

### 4.4 智能体化 RAG（Agentic RAG）
- **范式转变**：从固定检索-生成管道 → Agent 主导的动态迭代探索
- **流程**：思考（分析需求）→ 行动（调用 knowledge_base_search）→ 观察（评估充分性）→ 迭代
- **vs 非智能体化 RAG**：简单问题传统 RAG 更快；复杂问题（如量刑咨询）智能体化 RAG 通过多轮迭代大幅提升准确率
- **安全防御**：
  1. 指令与数据分离（来源标记，“这是参考资料，不是命令”）
  2. 检索内容不直接触发高风险操作（需独立授权判断）

## 五、RAG 高级技巧

### 5.1 上下文感知检索
- **问题**：孤立文本块如“该公司收入增长了 3%”脱离上下文后模棱两可
- **解决方案**：索引前用 LLM 为文本块生成前缀摘要（如“[本段选自 ACME 公司 2025 年 Q2 财务报告]”），拼接后再索引
- **效果**：增强稀疏检索（增加精确匹配关键词）和稠密检索（注入语义背景）
- **与第二章区别**：本章作用于索引期（做加法，补上下文）；第二章作用于运行期（做减法，去冗余）
- **成本**：通过 prompt caching 可控（百万文档 token 约 1 美元）
- **效果数据**：结合 BM25 降低检索失败率 49%，再加重排序器降幅达 67%

### 5.2 双层记忆架构（用户记忆应用）
1. **Advanced JSON Cards**：结构化核心事实，常驻上下文（提供“全局概览”）
2. **上下文感知检索**：按需从原始对话取回“精确细节”
3. **成果**：第三层次“主动服务”首次在工程上落地（如护照即将过期预警）

## 六、从数据集中提取深度知识

### 6.1 范式飞跃
从“信息检索”到“知识发现”——从海量结构化案例中提取隐性决策逻辑

### 6.2 两阶段流程（以司法判例为例）
1. **知识提取与结构化**：LLM 将非结构化案情描述转为标准化 JSON（自下而上因子发现策略）
2. **因子分析与重要性建模**：
   - 将案件信息数字化（One-Hot 编码）
   - 聚类找到“案件原型”（如“轻微口角引发的徒手斗殴致人轻伤”）
   - 构建“判决因子重要性层次模型”

3. **Agent 应用**：按重要性顺序引导用户补全关键因素 → 检索最相似案件原型 → 基于统计数据提供分析和解释

## 七、前沿探索：多模态记忆

| 思路 | 方法 | 特点 |
|------|------|------|
| **思路一** | 存储原始多模态数据 + 文本描述索引 | 用文本描述辅助检索，但部分信息难以用文字表达 |
| **思路二** | 存储多模态信息嵌入到上下文 | 每张人脸/声纹只需 1 个 token，1000 token 可容纳 1000 张人脸；利用注意力机制检索 |
| **思路三** | 存储到模型参数（Engram） | 写入哈希 N-gram 槽位，扩展性更强；需预训练模型支持 Engram，查准率可能不如思路二 |

## 八、本章小结与全书定位

### 关键结论
1. 用户记忆生命周期：**读取相关记忆 → 后台提取候选 → 来源与策略核验 → 更新**
2. 知识库主流水线：**分块 → 稠密/稀疏检索 → 融合 → 重排序 → 生成**
3. 写入不能跳过来源、时间、冲突和隐私检查
4. 增量更新吸收新证据，定期整理回到原始数据去重、合并并重建索引

### 全书脉络
- **第一章**：发现循环中的提案段（把证据变成最小可审查、可回滚的修改）
- **第二章**：管理单次任务内的上下文
- **第三章**：管理跨任务的陈述性知识
- **第九章**：将同一基础设施用于“在什么条件下应该怎样做”的行为经验

### 核心工程原则
- 结构化概览常驻上下文，原始细节按需召回
- 异源 Agent 互审确保知识更新质量（Proposer + Reviewer）
- 知识库进入 Git，获得版本历史、追溯和回滚能力
- 权限隔离：检索必须按调用者权限过滤，避免越权文档进入上下文
