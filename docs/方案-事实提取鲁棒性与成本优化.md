# 方案：事实提取鲁棒性与成本优化（待评审）

日期：2026-09-09 · 状态：**待评审（未实施）**
关联：layer2 首轮全量评测 run_98df5b6320（5/20 = 25%）失败归因——本次会话逐层定位；
涉及管线：`os_mem.extraction`（extractor / prompt）+ `os_mem.infra.llm`（deepseek_client / base_client）
+ `mem_settings` 提取参数。**不涉及**存储 schema、检索策略链、评测 harness。

## 1. 目标（本次改动范围）

1. **消除「截断 → 盲目重试 → 整段降级 → 写库崩溃」的浪费链**：时间、金钱、脆弱三害同源，
   均指向提取调用对「输出长度截断」这一确定性事件的错误处理。
2. **双维分段**（字符数 OR 消息数）把单次提取的产出需求压进输出预算，让提取「第 1 次就成功」。
3. **保命路径不自爆**：`raw_conversation` 整段降级不再撞 Milvus `value` varchar(1024) 上限。
4. **补观测**：成功调用 usage 落日志（现状 printf 风格参数在 loguru 下不渲染，全为裸 `%s`），
   支撑 4.2 参数校准与长期成本记账。

**非目标**：不做实体级主键 / as-of 版本裁决（layer2 矛盾·演进用例的系统性根因，工作量与
本方案不在一个量级，见 §8 另立文档）；不动检索策略链 / 回答 / 判定；不动 Milvus schema；
不做 LLM client「只替换 user message」类改造——**已核查：`get_llm_client()` 与
`get_structured_mem_service()` 均为进程级单例，OpenAI SDK 自带连接池，TCP/TLS 不重复握手，
多段并行共用同一 client，client 复用无需改动**。

## 2. 问题背景与证据（run_98df5b6320 日志量化）

layer2×struct×assert@top20 首轮：5/20 过，15 挂分两类——3 例基础设施崩（score=None，
Milvus 写入异常，未跑到回答阶段）+ 12 例质量失败。本方案只治前者及普遍的浪费形态：

| 证据 | 数值/出处 |
|---|---|
| 提取总调用 171 次，**97 次空 content（56.7%）** | 日志窗口 19:02–21:45Z，app-2026-09-08.jsonl |
| 空 content 输出 token 纯烧 ≈0.8M（每次 ≈8192） | completion_tokens=8192 = max_tokens=8192，恰好顶满 |
| 截断是**确定性**的：同段 attempt 1/2/3 全 `finish_reason=length` | 层2_10/13/20 崩溃前日志 |
| 单消息最长仅 169 字符；5.5~7.9KB 长文 = **整段会话序列化**（含 role 标记） | YAML 逐条统计 + 代码 `'\n'.join(messages)` |
| 5.5–7.9KB < 8000 字符分段阈值 → **单段硬扛**，输出预算爆 | chunk_dialog L131 `len<=max_chars → [整段]` |
| repair 续写 **15/15 全成功**（秒级、廉价）——但截断到空 content 时根本不触发 | 日志 repair 成功 15 次、repair 再失败 0 次 |
| 整段降级 3 次 → Milvus 崩 3 例（value 7909/6742/5502 > 1024） | `_degrade_fact` value=整段 dialog_text |
| 成功调用 usage **不在日志**（`chat ok ... in_tok=%s` 原样落盘） | loguru 不渲染 printf 风格位置参数 |
| 2.6h/20 例，重试风暴为主要耗时（单会话最坏 9 次 API、8+ 分钟） | 20:08–20:16 等连续空烧序列 |

**根因链**：输出预算 8192（大概率=模型硬顶，调大无路）是硬约束 → 决定产出的不是输入字符数
而是「要列多少条事实」≈消息数 → 现分段只看字符 8000，中长段（5.5–8KB/56–86 条消息）漏网单段
硬扛 → `finish_reason=length` 截断 → client 视为「空返回」指数重试 3 次（注释自述「length 应调大
max_tokens 而非盲目重试」但实现未做）→ 内容为空又绕过 repair → 整段重试 3 次 × client 3 次 = 9 次
空烧 → 降级 `raw_conversation`（value=整段，无长度防线）→ Milvus 1024 上限崩溃 → 整例无答案。

## 3. 设计

### 3.1 调用结果类型化 + 截断专用路径（治 D1/D2）

**问题**：`ChatClient.chat() -> str` 丢失 `finish_reason`；`content 空 + finish=length` 与
`content 空 + finish=stop` 被同等对待，都走指数重试。

**改动**：
1. `base_client` 增 `ChatOutcome(content, finish_reason, usage)`；client 增
   `chat_outcome(messages, ...)`，`chat()` 保持返回 str（answer 生成侧兼容，内部转调
   `chat_outcome().content`）。
2. `deepseek_client` 路由逻辑：
   - `content 空 + finish_reason=length` → **不重试**（确定性失败，重试必复现），立即返回
     outcome 上抛；日志记为「截断空返回」。
   - `content 非空`（无论 finish）→ 正常返回（截断 JSON 交给 repair，见下）。
   - `content 空 + 其他 finish_reason` → 保留原指数重试（真偶发）。
3. `extract_chunk` 分流（取代现在的「全败→整段重试」）：
   - 非空但解析失败（含 `Unterminated string` 截断形态）→ **repair 续写**（现状已有，保留）；
   - 空 content + length（截断且内容不可 repair）→ **对半切段递归重提一次**（depth ≤1）——
     用「更小的段」而非「同样的段再试」；两半都空则合并降级；
   - repair 失败 → 整段重试一次（现状，收敛为 1 次而非 3 次）；
   - 仍失败 → 走 3.3 降级。
4. 同段「整段重试」从 3 次降为 1 次（截断确定性已证，多次重试无信息增益）。

**效果**：单段最坏 ≈ repair 1 次 + 半段 1 次，不再 9 次空烧。

### 3.2 双维分段：字符数 OR 消息数（治 D3）

**问题**：分段只看输入字符 8000，而真实瓶颈是输出预算（由事实条数≈消息数决定）。
5.5–8KB 的「中长段」漏网单段硬扛；>8KB 反而切段安全。

**改动**：`chunk_dialog` 切分条件改为 **`chars > MAX_CHARS 或 messages > MAX_MSGS` 任一超限即切**，
重叠保留逻辑不变（按消息条数）。`settings` 参数（初值=保守估计，观测修复后按真实 usage 校准）：

| 参数 | 现值 | 新值 | 依据 |
|---|---|---|---|
| `DEEPSEEK_EXTRACT_MAX_CHARS` | 8000 | **4500** | 半量起步；防少数超长单条消息 |
| `DEEPSEEK_EXTRACT_MAX_MSGS`（新增） | — | **35** | layer2 会话 56–86 条 → 切 2–3 段；每段 ~30 条消息 ≈ 40–60 facts ≈ 2.5–3.5K tokens，< 8192 且留收尾余量 |
| `DEEPSEEK_EXTRACT_OVERLAP` | 5 | **3** | 段变小后 5 条冗余占比 ~17% 过高；3 条 + 既有 dedup 保证边界信息不丢 |
| `DEEPSEEK_EXTRACT_MAX_FACTS` | 100（全局语义） | **60（每段语义）** | 100×~70 tok ≈ 7000 逼近 8192，无收尾余量；分段后每段 60 足够，总量跨段不受限 |

**说明**：字符数与消息数都是「事实条数」的代理指标，各有盲区——仅按字符漏掉
「消息密集但每条短」，仅按消息漏掉「少数超长消息」。OR 语义保证两盲区互不穿透。

### 3.3 降级防线（治 D6a）

**问题**：`_degrade_fact` value=整段 dialog_text（5.5–7.9KB），超 Milvus `value` varchar(1024)；
LLM 全挂时恰是最需要写库兜底的时候，保命路径却自爆。

**改动**：`_degrade_fact` 输出切片——value 按固定窗口 ≤900 字符切多条（确定性边界，同会话重跑
产出同 key 集，投影删旧插新幂等收敛）；key 序列 `raw_conversation` / `raw_conversation_2` / …。
SQLite 侧不动（无长度限制，原文仍完整可审计）——只保护 Milvus 投影。

### 3.4 观测修复（治 D6b）

1. 修 `chat ok` 日志：printf 风格位置参数 → loguru 原生（f-string），`in_tok/out_tok/finish_reason`
   真实落盘。
2. `StrucMemService` 每会话记账一条 INFO：提取调用次数 / 截断次数 / repair 次数 / 输入·输出 tokens /
   耗时——下一轮评测后用真实数据校准 3.2 参数，并为长期成本记账。
3. 顺带约定：system prompt 保持字节稳定（无时间戳/动态内容），不打断 provider 侧自动前缀缓存。

## 4. 验证（纯逻辑单测，无 LLM；**不跑评测**）

- `chunk_dialog` 双维触发矩阵：仅字符超 / 仅消息超 / 都超 / 都不超；overlap 冗余条数；切分确定性。
- `_degrade_fact`：900 切片边界、key 序列、同输入幂等。
- client outcome 路由：mock finish_reason（length / stop）→ 断言是否重试 / 是否上抛。
- `extract_chunk` 分流：fake complete 注入「截断空返回」「非空坏 JSON」「正常」→ 断言 repair /
  半段递归 / 降级各路径。
- 日志断言：`chat ok` 渲染后含真实 usage（不再含 `%s`）。
- 落点：扩展现有 `tests/test_fact_extraction.py`（或新 `tests/test_extract_chunking.py`）。

## 5. 执行顺序与提交

按依赖分 4 个 commit（中文 message，含背景/改动/验证；**commit 后立即 push origin main**）：
1. base_client `ChatOutcome` + deepseek client 截断路由（3.1 前半）
2. extract_chunk 分流 + 整段重试收敛 1 次（3.1 后半）
3. 双维分段 + settings 参数（3.2）
4. 降级切片 + 观测修复（3.3/3.4）
每步跑相关纯逻辑单测通过后再提交。**全部落地前不启动任何评测**。

## 6. 风险

| 风险 | 缓解 |
|---|---|
| 分段增多 → 调用次数增加 | 每段大概率第 1 次成功；当前最坏 9 次空烧 vs 分段后 2–3 段 ×1 次 + 偶发 repair → 净成本应下降，3.4 观测验证 |
| 对半切递归遇超长单条消息（>4500 字符一条）无效 | 罕见（layer 用例单消息 ≤170 字符）；兜底=该条整体降级 verbatim，不阻塞批次 |
| 每段 60 facts 上限在某高密度段截断 | repair 兜底（3.1），且跨段总量不受限 |
| 参数初值偏保守/偏激进 | 3.4 观测落地后按真实 usage 校准，一次设置改动即调 |

## 7. 范围外（另立文档，本方案落地后再立项）

**实体级主键 + as-of 版本裁决（D4/D5）**：现设计是「句子级扁平句袋」，key 由 LLM 自由拟，
跨会话同实体 key 漂移（amount / original_amount / final_amount 并存）→ Milvus
「按 (cat,key) 删旧插新」的投影收敛被架空 → 新旧版本并存全注入，矛盾裁决责任被推给回答 LLM。
这是 layer2 矛盾/演进用例（12/15/16/18 等）过不了关的系统性根因，同时是「每会话全量重提取」
结构性成本（重复劳动 + 漂移放大器）的来源。方向：实体/属性/变更语义 + 提取增量并与既有记忆
差分合并。工作量与影响面大，须单独出方案评审。
