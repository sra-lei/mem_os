## 1. 动机

排查「D4 改了提取/入库侧，本地 memories.db 是否已经落后」时确认：本地库是 **2026-09-09 17:44
`run_70251777e5`** 那批数据，坐标在 **D4-1 之后、D4-2（09-12 13:29）与 Fix B（09-12 16:51）之前**。
它在 D4 语义上是「缺一整代机制」的数据（实体全 SELF、零版本链、R1 静默丢失仍在），
而项目铁律 2 规定：**改提取侧后不清缓存，重跑会因 claim 命中 COMPLETED 而跳过提取，测到旧数据且不报错**。

- 结论：**要 D4 口径的数据只能重提取**（entity_ref/attribute/lifecycle/版本链都是入库时算出来的，无回填路径）。

## 5. 判读

1. **数据层：D4 目标达成**。实体归属生效（35 行非 SELF，含 `DRUG:`/`CARD:` 两种 v2 新种类）、
   签名唯一性无违反、静默丢失的两个代表 token 回到库里。这是同步路线给不了的结果。
2. **指标层：layer1 上看不出 D4 的任何效果**。±2 例的变化完全落在历史噪声带内
   （同配置单轮就能在 10~14/20 之间摆，均分 0.668~0.802）。两进两出、方向互相抵消，
   不足以支撑任何「收益」或「回归」结论。**本轮 12/20 也未复现待办清单快照里的 14/20**
   （`run_452ba69d36`，另一台机器，见 §4.1）——差 2 例正好等于离散度本身。
3. **与 D4 的设计意图一致**：D4 解决的是**跨会话**的实体归属与 as-of 版本裁决，而 layer1 每例单会话——
   版本裁决不触发、实体也多归 SELF（本轮 35/933 ≈ 3.8%）。D4 的战场是 layer2（12 电汇 / 10 改签 /
   11 诊疗 / 20 医保这类矛盾演进题）。
4. **一个反直觉但重要的推论**：**修好记忆数据 ≠ layer1 涨分**。layer1 的稳定弱项（11/13/15/17）
   是「多数字回忆+汇总」类，瓶颈在注入窗口与答案侧，而不在数据的版本裁决。
5. **读分纪律**（待办清单 P0-2）：单轮跑分不可比，判 D4 收益须同配置 ×3 轮取均值，或直接看 layer2。

## 6. 结论与下一步

1. **本地记忆库现在已是 D4 口径**（933 行，20 user），可直接作为后续 layer1 对照的基线数据。
2. **D4-5（全量 layer2 复测）仍未跑，且本地 layer2 数据为零**：需先按同一套流程清缓存再跑 layer2——
   那才是能体现版本裁决与实体归属收益的场景。参数（provider / top-k / judge）待定。
3. **想让本机结论与快照可比，二选一**：把另一台机器的 `run_452ba69d36` / `run_2bf4dafd1b` 及其
   memories 同步进本机（`evals/runs/` + `memos.db`，逐例数据齐全后才能与 §4 的表并列），
   或按待办清单 P0-2 在本机**同配置 ×3 轮取均值**建立稳定基线后再判 D4 收益。
3. **`scripts/audit_silent_loss.py` 目前跑不了**：它读 `conv_messages`，而 struct provider 的 ingest
   **不写原文**（只有 base provider 写；本轮重跑后 `conv_messages` 仍为 0）。想让 Fix B 的「归零」
   用审计脚本当回归闸门，得先让原文落库（跑一轮 `--memory-provider base`，或给 ingest 补落原文入口）。
4. 顺带观测（可作 D4-2 v2 的正面证据）：v2 的实体种类从 v1 的 `ID:`/`PROD:` 扩到了 `DRUG:`/`CARD:`，
   多值属性靠「实例实体 + 属性剥离」表达，未见签名冲突。
5. 待办文档项：导出/导入不带 D4 身份字段（13.9-8）、界面不显示 lifecycle/entity/attribute（13.9-9）；
   AGENTS.md §7 关于 `memories.db` 被白名单追踪用于跨机同步的说法已与现状不符（09-06 起已移出追踪）。
