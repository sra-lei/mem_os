## 4. case 11 的真根因（**答案 prompt 修不了**）

新 prompt 下模型确实照规则"先列后算"了，但算出的口径是错的：

```
你提到的流动性资产（非退休账户）合计为 $248,500：
- Wells Fargo 储蓄：$67,000
- Chase 支票：$18,500
- Vanguard 券商账户：约 $125,000      ← 投资账户，判分口径应排除
- TD Ameritrade：$38,000              ← 同上
计算：67,000 + 18,500 + 125,000 + 38,000 = $248,500
```

问题定义"liquid assets"在**问题原文**里（`What was my total liquid assets amount…`），
模型把券商账户也算成流动——但更根本的是：**判分要的第三项 `Marcus 高收益储蓄 $45,000`
在库里根本不存在**（详见 §5）。也就是说 `$130,500` 这个合计**物理上无法从档案算出**，
prompt 再怎么写也无解。

> 审计工具的口径局限（记录备查）：它按 token 匹配判"提取漏"，而库里存在**另一个 $45,000**
> （`condo_sale_profit` 公寓售出利润），于是把"45,000 已存在"记为命中 → **掩盖了这处真提取漏**。
> 同名数字属不同实体时，token 级审计不可信。

## 5. 附带发现（E 类，最高优先）：R1 剪枝的实体绑定盲区

对话原文里的句子（`layer1_11`）：

```
I have $67,000 in my Wells Fargo savings and another $45,000 in a Marcus by Goldman Sachs high-yield savings.
```

它含精确 token，**本应被 verbatim 兜底留下**。但生产代码实测：

| 检查 | 结果 |
|---|---|
| 该句 `fact_tokens` | `['45000', '67000']` |
| 该 user 结构化 token 是否覆盖它 | 是（子集判据成立） |
| 覆盖者 | `condo_sale_profit`（**$45,000 公寓利润**）、`savings_balance`/`savings_account_balance`（Wells $67,000） |
| `RegularExtractor.prune_redundant_verbatim(fallback, llm_facts)` | **剪掉（不存）** |
| 库内 verbatim 行含 "Marcus" | **0** |

即 R1 的判据「**精确 token 集 ⊆ 结构化 token 集**」忽略了**实体绑定**：
同一个数字被**另一个实体**占用时，句子仍被判冗余而丢弃，`Marcus=45,000` 这条
「数字↔实体」的绑定**在入库时永久丢失**——这正是 case 11 恒定失败的根源。

这是仓库既知"静默丢失"家族的新变体（此前 Fix B 处理的是"批内收敛丢弃载体"那条路径）。

### 建议方向（提取侧，需先立方案）

1. **判据加实体线索**：仅当覆盖 token 的结构化事实与兜底句存在词汇/实体重叠（如句内关键名词）
   才判冗余；否则保留；
2. **或按"数字-属性配对"比较**（需要轻量解析：数字邻域词 vs structured key/attribute）；
3. **或显著放宽 / 停用 R1**：宽窗架构下"多存"的成本已很低（预算内全入、46 行/例、
   预算 12k 只用了 88% 的最坏情况），而 R1 的收益只是省空间——**它的性价比与本项目
   当前形态已经反转**。这条与检索侧简化的结论同源：把裁决交给宽窗，入库侧宁多存。

## 6. 结论

1. **答案层收口有效**：15/16 两例三轮全过，均值 17.3 → 18.3，其余 16 例无回退；
   代价是输出 token +29%、时长 +5~8%（可接受）。
2. **layer1 剩余的两例失分都不在答案层**：`11` = R1 实体绑定盲区（E 类），
   `04` = 兜底口径漏短代号（D 类）——两者都是**提取侧**，检索侧无需再动（覆盖漏已为 0）。
3. 因此下一步的性价比排序变为：**E 类（R1 判据）→ D 类（短代号口径）→ A6（投影一致性）**，
   而不是继续调答案或检索。
4. **宽窗与 prompt 是协同关系**（§7 的 2×2 证据）：窄窗下 prompt 改动零效果；
   宽窗是主变量（13 → 17.3/18.3），prompt 是次变量（宽窗下 +1 例均值，修好 15/16）。
   另外，宽窗把"确定性失败（缺值）"换成"概率性失败（答全率）"——均值大涨、
   单轮方差也随之变大（窄窗 4 轮极差 0；宽窗 6 轮极差 3）。

## 7. 2×2 交叉验证：宽窗 × 答案 prompt（决定谁是主变量）

把检索侧临时恢复到"窄窗态"（`git checkout 181b8a2 -- src/os_mem/core/retrieve/... struc_mem_service.py`：
5 段策略链 + `fetch=top_k×3` + 截断 15），answer prompt 保持新版，跑 3 轮，
补上 2×2 的最后一格：

| 检索口径 ↓ / answer prompt → | 旧 prompt `7251aaf2ed08` | 新 prompt `d788d0b3c96d` |
|---|---|---|
| **窄窗**（5 段链 + ×3 + top_k=15） | `run_3776d38c12` **13/20**<br>挂 04 11 13 15 17 18 19 | `run_347b1072f4` / `run_470d3f3111` / `run_6911f61e2e`<br>**13 / 13 / 13**，失败集与左侧**逐例相同** |
| **宽窗**（fetch=256 + 字符预算 + 链清空） | `run_8c4be3630c`/`e54cf0bd81`/`9278f58a73`<br>19 / 16 / 17（均值 **17.3**） | `run_8b7b04bc29`/`c5027b2693`/`d79577c662`<br>19 / 18 / 18（均值 **18.3**） |

**结论**：

1. **窄窗下 prompt 改动零效果**：三轮 13/20、失败集与旧 prompt 的窄窗轮完全一致
   —— 那些 case 在窄窗下缺的是**覆盖**（窗内没有需要的值），prompt 再强调"列全"也无从下手。
2. **宽窗是主变量**：13 → 17.3（旧 prompt）/ **18.3**（新 prompt），跨两种 prompt 都成立（+4~5 例）。
3. **prompt 是次变量且依赖宽窗**：宽窗下 17.3 → 18.3（+1 例均值），修好 `15`/`16` 的
   "窗内有值却不答"。二者是**协同**关系：宽窗提供全部素材，prompt 保证不遗漏。
4. 由此回答"历史上的 k=30 稀释"：那是**混合效应**——k=30 时覆盖漏仍剩 5 点（覆盖不足），
   同时窗内值被漏答（答全率）。本实验把两者分离：**覆盖归宽窗，答全归 prompt**。

### 7.1 伴随观察：宽窗把"确定性失败"换成了"概率性失败"

| 口径 | 单轮通过 | 极差 |
|---|---|---|
| 窄窗（4 轮，含 A 组） | 13 / 13 / 13 / 13 | **0** |
| 宽窗（6 轮） | 19 / 16 / 17 / 19 / 18 / 18 | **3** |

窄窗的失败是**确定性**的（缺值 → 必然答不出）；宽窗下素材齐全，成败变成"模型是否用全"
→ **概率性**。这解释了实验记录里"±2~3 例离散"的来源，也给出判读纪律的依据：
**宽窗形态下更必须多轮取均值**，而窄窗形态下的单轮结果反而稳定（但稳定地低）。

### 7.2 与"入库清洗"的关系：**排除性结论——不是它**

问题起于一个合理猜测：宽窗下"答不全"的现象消失了，是否因为入库清洗（D4-2 v2 归一/实体
解析 + 签名唯一性）让窗口更干净。2×2 数据可以直接排除：

| 检查 | 结果 |
|---|---|
| 同一份 **D4 清洗后**的库 + 宽窗 + **旧** prompt | `15` 挂 2/3、`16` 挂 1/3，审计归因是**回答漏**（窗内有值未答） → 现象**仍复现** |
| 同一份库 + 宽窗 + **新** prompt | `15`/`16` 三轮全过 → 现象消失 |
| 同一份库 + **窄窗** + 新 prompt | 13/13/13、失败集与旧 prompt 逐例相同 → prompt 在窄窗下**无任何效果** |

即：**入库清洗既不是该现象的成因，也不是它的解法**。真正的分工是：

| 缺口类型 | 由谁负责 | 证据 |
|---|---|---|
| **覆盖**（窗内有没有） | **检索侧：宽窗** | 13 → 17.3/18.3；覆盖漏在宽窗下归零（layer1） |
| **答全**（窗内有值却漏答） | **答案侧：prompt** | 宽窗下 17.3 → 18.3，15/16 三轮全过 |
| **答错值 / 新旧混值** | **入库侧：D4 归一 + 实体解析 + 签名唯一性** | case 05 两条 `account_number` 曾互撞，D4-2 拆成 `ID:VEL\|account_number` 与 `SELF\|account_number` |
| **判分形式对不上** | 入库侧：提取兜底口径 | `12C` 被改写成 "Row 12, seat C"（D 类） |
| 静默丢信息 | 入库侧：R1 判据 | Marcus 余额被当冗余剪掉（E 类） |

一句话：**"入库清洗"改善的是"答错/混值"，不是"答不全"**；后者的对症解在答案侧，
且以宽窗为前提。
